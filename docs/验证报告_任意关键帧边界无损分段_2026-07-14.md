## 2. 落地合同

### 数据与数学

- 用户创作曲线继续使用 `cubic_bezier` + 四个 `[0,1]` 控制点；旧五种 preset 公式不变。
- split/trim 在项目整数帧上求切点，用 De Casteljau 生成左右子曲线并保持“目标关键帧控制入段”。
- 派生曲线使用只读 `derived_monotone`，允许单调分段自然产生的框外控制点，不做 clamp。
- v2 `sourceWindow` 保存原 easing、原曲线和原整数帧窗口。
- v2 `sourceTransform` 保存原入段首尾位置、缩放和旋转。
- 核心预览与 FFmpeg 直接用 `sourceWindow + sourceTransform` 求原轨迹；舍入后的 child boundary 仅用于结构/交换，不是语义权威。
- `hold` 仍只在原目标帧跳变；末关键帧后的常量尾段保持静态。

### 编辑器、CAS 与 OTIO

- split、trim-start、trim-end 共用一个关键帧分区 helper。
- 右片段把切点 transform 写入静态基值，不制造伪 F0 关键帧；split 右段重生 ID，trim 保留原 ID。
- 工程 JSON、`update_clip`、revision CAS、持久 undo/redo 和命令账本继续使用同一状态源。
- 无派生曲线时 OTIO 写 `aicanvas.cubic-bezier.v1`；含派生曲线时写 v2。
- 导入接受 v1/v2，拒绝未知合同、v1 携带 derived、缺失 source anchors、窗口长度不一致或锚点篡改。
- MCP 工具数保持 133；`get_capabilities.editor.keyframeCurves.editing.arbitraryCurveSubdivision=true`。

### Electron UI

- 现有“分割”和画中画边缘裁切直接走原子 `split_clip` / `trim_to_playhead`。
- 派生 easing、四点输入和控制柄只读；SVG 仍显示真实原窗口曲线，框外派生点不被截断。
- pointercancel 从手势快照恢复预览且不落盘；pointerup 恢复本地预览后提交原子裁切。

## 3. 2 px 漂移根因与修复

病态合法曲线 `{x1:1,y1:0,x2:0,y2:1}` 的 trim-end 曾在 F24 留下约 2 px 偏移。独立表达式核验得到：

- baseline：`-110 + 220 × 0.5 = 0`；
- 旧派生路径：从 12 位舍入 child boundary 再反算 affine，得到约 `-1.4210854715202e-13`；
- FFmpeg root、帧变量、enable 和 scale 均正确；
- yuv420 overlay 把微小负数吸附到前一个偶数色度网格，放大为 2 px。

因此没有提高容差、添加 epsilon 或只增加小数位。修复是保存并直接使用原段 transform anchors。

2026-07-14 10:20 的当前源码复跑进一步把“空间语义”和“交付编码差异”拆开：

- 核心求值严格比较：split 49 个端点/帧、trim-start 36 个端点/帧、trim-end 32 个端点/帧，`positionX / positionY / scale / rotation` 最大绝对差均为 **0**；
- 使用当前产品 FFmpeg 图逐帧提取 PNG，再解码为 RGB 比较：split 48 帧、trim-start 35 帧、trim-end 31 帧，三组 `changedFrames=0`、`changedChannels=0`、`maximumChannelDifference=0`，分段前后 raw SHA-256 各自完全相同；
- baseline 与 split H.264 MP4 仍逐字节同 SHA-256，48 帧全部解码指标为 0；
- trim 会改变可见区间，x264 GOP/lookahead 因而产生有损量化差异：trim-start 最大质心阈值差 `0.051358 px`、bbox `0`；trim-end 为 `0.434767 px`、bbox 最大 `1`。这些差异只记录为 codec diagnostic，不再作为关键帧空间语义容差，也不用于声称逐像素相同；
- 旧报告中“trim 的 H.264 质心/包围盒/红像素全部为 0”与可复跑结果不一致，现已纠正。无损结论由上面严格为 0 的核心与 pre-encode/lossless 证据承担。
