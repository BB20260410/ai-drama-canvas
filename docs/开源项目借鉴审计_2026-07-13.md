# 开源项目借鉴审计（2026-07-13）

## 1. 审计范围与结论

本轮只使用项目官方仓库、官方 API 文档和官方开发文档，重点核对六类能力：素材版本、导演审片、编辑恢复、生成队列、许可证和可集成边界。没有扫描任何真实漫剧项目，也没有复制第三方实现。

当前项目已经具备稳定素材 ID、真实路径与 `aicanvas://` URI、权威版本选择、派生关系、绑定素材 ID/SHA-256 的追加式视觉验收、持久化剪辑撤销/重做、OTIO 交换、后台渲染恢复、生成提交意图、`submission_unknown` 对账和外部任务 ID。因此，本审计不再重复建议这些已完成能力，而只记录尚有增量价值的结构。

最终决策：

| 项目 | 许可证 | 最值得借鉴 | 当前决策 |
|---|---|---|---|
| OpenAssetIO | Apache-2.0 | 发布前预检、逻辑实体引用、解析上下文、批量注册 | 进入长期兼容设计；暂不引入运行时依赖 |
| Kitsu + Zou | AGPL-3.0 | 任务—评论—预览修订—审核状态—主预览闭环 | 借鉴审片数据结构；多人协作时再做外部连接器 |
| OpenCut | MIT | Editor API、插件优先、Headless、MCP 的方向 | 观察，不基于当前重写版实施核心功能 |
| LosslessCut | GPL-2.0-only | 小型可恢复工程文件、无损快切、片段标签 | 借鉴概念；不复制或链接代码 |
| Revideo | MIT | TypeScript 参数化视频模板、无头渲染、并行分段 | P2 实验适配器，用于片头/字幕/包装，不替代剪辑台 |
| ComfyUI | GPL-3.0 | 不可变工作流快照、异步队列、历史对账、节点级进度 | P1 外部本机适配器，通过 HTTP/WebSocket 连接 |

## 2. 当前代码的真实缺口

与这些项目对照后，当前项目仍有四个值得补齐的缺口：

1. 素材发布虽然已有稳定输出路径和不可覆盖规则，但还没有独立的“发布预检/预留/最终注册”通用合同，生成、剪辑导出和外部工具登记仍各自处理输出意图。
2. 视频审片已有版本对照和逐项结论，但缺少绑定到具体时间码或画面坐标的批注；返工原因仍主要是整条记录级文本。
3. 剪辑工程已有持久撤销与渲染恢复，但没有面向纯裁切/重排任务的无损快速导出路径，也没有显式的“异常退出后恢复哪个工程修订”启动选择。
4. 生成队列已有可靠提交意图和供应商对账，但尚未保存“实际执行工作流 JSON + 工作流哈希 + 节点/模型环境快照”，也没有 ComfyUI 节点级执行进度。

## 3. OpenAssetIO：只引入边界思想，不把它误当资产数据库

### 官方事实

OpenAssetIO 是 Host 与 Asset Management System 之间的抽象 API，本身“没有固有功能”，负责用不透明实体引用、Traits 和 Manager 插件连接已有资产系统，而不是提供现成的资产数据库。[官方介绍](https://docs.openassetio.org/OpenAssetIO/)

实体可以有多个版本和关系；Host 通过 Traits 请求位置、图像、播放等语义，避免只靠扩展名和路径猜测。[实体、Traits 与规格](https://docs.openassetio.org/OpenAssetIO/entities_traits_and_specifications.html)

它的发布流程分为 `preflight` 与 `register`：预检可验证输入、分配存储位置或锁定版本，并允许 Manager 返回新的具体版本引用；数据生成后再注册最终 Traits 和位置。[发布语义](https://docs.openassetio.org/OpenAssetIO/glossary.html#publish)

当前官方仓库已经发布 1.0 系列；许可证为 Apache-2.0。[官方 Releases](https://github.com/OpenAssetIO/OpenAssetIO/releases)、[许可证](https://github.com/OpenAssetIO/OpenAssetIO/blob/main/LICENSE)

### 可借鉴结构

- 把 `aicanvas://projects/.../artifacts/...` 明确为逻辑实体引用，绝对路径只是可解析属性，不是身份。
- 将输出行为统一成 `preflightPublication → write new file → verify → registerPublication`。预检结果至少包含逻辑实体、预留版本、允许写入根、预期路径、调用上下文和幂等键。
- 解析时携带用途上下文，例如 `preview`、`generation-input`、`final-render`；同一素材未来可解析到代理文件、原图或迁移后的新根。
- 保持批量优先：一次解析或注册一批素材，逐项返回成功/失败，不因单项失败丢失整批证据。OpenAssetIO 的 Manager 接口也明确以 batch-first 为目标。[Manager 接口](https://docs.openassetio.org/OpenAssetIO/classopenassetio_1_1v1_1_1manager_api_1_1_manager_interface.html)

### 集成成本与风险

OpenAssetIO 官方插件体系是 Python、C++ 或混合插件，通过环境变量发现 Manager；当前项目是 Electron/TypeScript，没有官方 TypeScript Host 路径。[运行时配置](https://docs.openassetio.org/OpenAssetIO/runtime_configuration.html)

现在直接嵌入会新增 Python/C++ 运行时、插件部署和跨语言故障面，而本项目仍是单机、文件系统事实源，也没有第二个资产管理系统需要互操作。为一个尚不存在的外部 Manager 引入整套运行时，收益小于成本。

### 决策

进入数据边界设计，但不进入近期依赖：

- P1：在当前 TypeScript 核心内实现轻量发布合同，复用 OpenAssetIO 的预检/注册语义，不复制其 API。
- P3：只有出现 Ayon、ftrack、Kitsu 或多个 DCC 共同解析素材的真实需求后，再评估独立 Python sidecar Manager；该进程只能通过受控 stdio/本机 IPC 连接。

## 4. Kitsu / Zou：审片模型值得借鉴，完整服务不适合首版单机工作流

### 官方事实

Kitsu 是协作前端，Zou 是其 Flask API 和生产数据“记忆层”；两者均为 AGPL-3.0。[Kitsu 仓库](https://github.com/cgwire/kitsu)、[Zou 仓库](https://github.com/cgwire/zou)

Zou 能存储项目、镜头、资产、任务、文件元数据、验证结果和带版本的预览文件，并发布变更事件流。[Zou 官方说明](https://github.com/cgwire/zou)

审片数据不是孤立的“通过/失败”按钮，而是围绕任务组织：评论下创建预览，预览 `revision` 默认自动递增；提交审核可以同时创建预览并可选改变任务状态；任务最后一个预览可被设为实体的主预览。[添加预览](https://api-docs.kitsu.cloud/operation/operation-post-actions-tasks-parameter-comments-parameter-add-preview)、[提交审核](https://api-docs.kitsu.cloud/operation/operation-put-actions-tasks-parameter-to-review)、[设置主预览](https://api-docs.kitsu.cloud/operation/operation-put-actions-tasks-parameter-set-main-preview)

Kitsu 还提供机器人账号、作用域和事件监听，适合外部流水线自动化。[机器人文档](https://dev.kitsu.cloud/guides/bot-automation)

### 可借鉴结构

- 保持“审片提交”原子化：版本快照、说明、审核状态变化和通知事件属于同一次命令，不能先改状态再补证据。
- 在当前 `ReviewRecord` 上增加可选 `annotations[]`：`artifactId`、`timeFrame/timeSeconds`、标准化坐标、批注文本、创建者、创建时间。视频返工可以直接定位帧和区域。
- 将当前权威素材选择理解为 Kitsu 的 main preview，但不新增第二套“主版本”字段；继续以 `authoritative artifact` 为唯一事实。
- 保留预览修订号作为展示序号，真正身份仍使用不可变素材 ID + SHA-256，避免仅凭 `v003` 误认文件。

### 集成成本与风险

完整自托管需要数据库、预览存储、用户/权限、备份和服务运维；官方旧部署文档也明确建议将数据库和预览目录分离。[Zou 部署说明](https://zou.cg-wire.com/)

当前是个人本机工作流，引入 Kitsu 会制造第二事实源和双向同步冲突。AGPL 也意味着不能把 Kitsu/Zou 源码直接并入当前桌面应用而忽略分发与网络服务义务；若未来连接，应保持独立服务 + REST API 边界，并在发布前做许可证复核。

### 决策

- P1：只实现时间码/画面坐标批注，沿用现有本地审片记录和命令账本。
- P3：出现多人制片、外部审核链接、供应商账号与权限需求时，新增可选 `KitsuAdapter`；默认单向发布预览与读取审核结论，不让 Kitsu 覆盖本地权威文件。
- 不进入：Kitsu 前端、Zou 数据库模型和权限系统不复制进当前应用。

### P1 落地记录（2026-07-13）

本地审片记录现已支持 clean-room 实现的版本批注，不包含 Kitsu/Zou 源码：

- 每条批注必须绑定本次验收 `artifactIds` 中的不可变 `artifactId`，不能只绑定节点或路径。
- 批注类型固定为 `issue`、`keep`、`question`、`continuity`；正文最长 2,000 字。
- 画面落点保存为相对素材内容区域的标准化 `x/y` 坐标，两个轴都必须在 `0..1`。
- 视频批注可保存 `timeSeconds`；当机械探测已有素材时长时，提交层拒绝越界时间码。图片批注拒绝携带视频时间码。
- `submit_review` 桌面 IPC、MCP 直接工具和 `execute_command` 幂等命令使用同一批注输入合同；持久化记录补充批注 ID、创建者和创建时间。
- ReviewStudio 支持在 A/B 具体版本画面上落点、暂停视频后记录当前时间码、编辑批注类型与内容，并在历史记录和画面上重放落点。
- “视觉通过”不能携带问题或疑问批注；“返工”可由问题批注作为明确返工证据。

## 5. OpenCut：方向相似，但当前版本不应成为实现基线

### 官方事实

OpenCut 主仓库正在从头重写，官方 README 把 Editor API、插件优先架构、Rust Core、MCP、Headless 和批量渲染列为“正在到来”的能力；官方同时说明当前可用版本仍是 classic。[主仓库](https://github.com/OpenCut-app/OpenCut)

`opencut-classic` 已归档，主仓库与 classic 均为 MIT。[classic 仓库](https://github.com/OpenCut-app/opencut-classic)、[主仓库许可证](https://github.com/OpenCut-app/OpenCut/blob/main/LICENSE)

### 可借鉴结构

它的路线与本项目现有方向高度重合：编辑 API 与 UI 分离、插件优先、Agent/MCP、Headless 渲染。因此它更适合作为架构方向的外部验证，而不是新的功能来源。

### 集成成本与风险

- 重写中的接口、数据模型和 Rust Core 仍可能变化，不能把路线图当稳定 API。
- classic 已归档，移植其浏览器存储或旧编辑状态会引入无人维护的历史结构。
- 当前项目已经有整数帧模型、OTIO、FFmpeg 导出、持久历史和 MCP；换成 OpenCut 会造成编辑内核重写，而不是增量集成。

### 决策

观察，不进入当前迭代。每个正式版本只复核一次其 Editor API、Headless 和 MCP 是否已发布稳定接口；在此之前不复制 UI、不移植 classic 状态管理，也不为它预留核心抽象。

## 6. LosslessCut：借鉴恢复文件和无损快切，不借代码

### 官方事实

LosslessCut 是以 FFmpeg 为核心的快速裁切/重封装工具，不是完整非线性编辑器。它保持原文件不变，用片段的入点、出点、标签和顺序描述导出内容；`.llc` JSON5 工程文件用于退出后继续工作，并支持撤销/重做及多种片段格式导入导出，当前版本也提供基础 OTIO 导入。[官方仓库](https://github.com/mifi/lossless-cut)、[官方使用文档](https://github.com/mifi/lossless-cut/blob/master/docs/index.md)、[官方 Releases](https://github.com/mifi/lossless-cut/releases)

许可证为 GPL-2.0-only。[package.json](https://github.com/mifi/lossless-cut/blob/master/package.json)、[许可证](https://github.com/mifi/lossless-cut/blob/master/LICENSE)

### 可借鉴结构

- 为剪辑工程增加很小的 `editor-session.json`：最近工程、最近稳定修订、是否正常关闭、未完成渲染 ID。异常退出后明确提示“恢复稳定修订 / 打开最新修订”，而不是静默猜测。
- 增加“无损快速导出”计划器：只有纯裁切、重排、兼容编码参数、无变速/滤镜/变换/字幕/混音时才允许 `-c copy`；否则明确回退当前 H.264 渲染。
- 片段标签和 tags 可进入镜头检索，但不另造一套项目文件；继续使用当前剪辑工程 JSON。

### 集成成本与风险

无损裁切受关键帧和流参数限制，入点可能被调整到前一个关键帧；它不能替代当前合成、画中画、关键帧、字幕和混音导出。官方也明确其不是完整 NLE。[官方 FAQ](https://github.com/mifi/lossless-cut/blob/master/docs/index.md)

GPL-2.0-only 不适合直接复制或链接进当前应用；本项目只 clean-room 实现 FFmpeg 能力探测与命令规划。若用户已安装 LosslessCut，可把 `.llc`/CSV/OTIO 当外部交换格式，但不把其源码打包进应用。

### 决策

- P1（已实现）：增加异常退出恢复选择器。状态只保存在轻量 `editor-session.json`，复用既有剪辑工程与 history；异常退出后的导演台被恢复选择器阻塞，用户必须选择“恢复最近稳定修订”或“打开最新修订”。恢复历史快照时创建新的更高修订，不覆盖当前或历史版本；正常关闭才把最新修订提升为稳定修订，恢复选择未完成时关闭仍保持异常状态。
- P2：增加严格能力门禁的无损快速导出；默认仍走现有可验证重编码路径。
- 不进入：不复制 LosslessCut 实现，不把它作为剪辑核心依赖。

## 7. Revideo：适合参数化包装模板，不适合承担项目队列

### 官方事实

Revideo 是 MIT 许可的 TypeScript 程序化视频框架，提供 React 预览、参数化模板和无头渲染；它由 Motion Canvas 分叉，重点是作为库和渲染 API 使用。[官方仓库](https://github.com/redotvideo/revideo)、[许可证](https://github.com/redotvideo/revideo/blob/main/LICENSE)

`renderVideo()` 在 Node.js 中启动无头浏览器，支持输出范围、尺寸、FFmpeg 路径、进度回调和多个 worker；多个 worker 会把时间范围分段并行处理。[renderVideo API](https://docs.re.video/api/renderer/renderVideo/)

CLI 服务可返回 `jobId`，并通过 callback 报告成功或失败，但完成文件下载链接默认只保留短时间。官方托管平台的 endpoint 也以模板部署和回调为主。[本地渲染端点](https://docs.re.video/render-endpoint/)、[平台端点](https://docs.re.video/platform/render-endpoint/)

### 可借鉴结构

- 用版本化 TypeScript 模板制作片头、集标题、字幕包装、演职员表和固定转场，而不是让用户每次手工搭时间线。
- 每次渲染登记 `templateId`、模板代码版本/提交哈希、变量 JSON、素材 ID、Revideo 版本和输出 SHA-256。
- Revideo 只做 Renderer；可靠队列、幂等键、重试、取消、下载和最终登记继续由当前应用负责。

### 集成成本与风险

Revideo 会引入 Puppeteer/无头 Chromium、Vite 端口、WebCodecs 与额外 FFmpeg 进程。并行 worker 内存开销明显，官方也提醒工作站通常不一定从多 worker 获益。[渲染性能说明](https://docs.re.video/common-issues/slow-rendering/)

不同视频格式会走 WebCodecs、FFmpeg 或慢速浏览器 seek 路径；模板代码本身也是可执行代码，必须限定在应用自带或用户明确允许的项目模板目录。官方开源版本默认有匿名遥测，可通过 `DISABLE_TELEMETRY=true` 关闭。[官方仓库](https://github.com/redotvideo/revideo)

### 决策

P2 做可选实验适配器，优先覆盖无外部插件的 2–3 个内置包装模板。以受控子进程运行、默认关闭遥测、固定版本、禁止任意远程模板。它不替代导演剪辑台，也不成为通用生成队列。

## 8. ComfyUI：最值得进入当前项目的外部生成适配器

### 官方事实

ComfyUI Core 当前由 `Comfy-Org/ComfyUI` 维护，许可证为 GPL-3.0。它原生提供异步队列，只重跑发生变化的工作流部分，并支持图像、视频、音频等节点工作流。[官方仓库](https://github.com/Comfy-Org/ComfyUI)、[许可证](https://github.com/Comfy-Org/ComfyUI/blob/master/LICENSE)

本机服务的关键接口已经足够形成可靠适配器：`POST /prompt` 会先验证工作流，再返回 `prompt_id` 和队列位置；`/ws` 推送执行开始、节点执行、进度、完成和错误；`/queue` 查询或管理队列；`/history/{prompt_id}` 用于恢复后对账；`/interrupt` 中断当前执行。[服务路由](https://docs.comfy.org/development/comfyui-server/comms_routes)、[WebSocket 消息](https://docs.comfy.org/development/comfyui-server/comms_messages)

客户端提交的是完整工作流快照；入队后再编辑画布不会改变已提交任务。[服务通信概览](https://docs.comfy.org/development/comfyui-server/comms_overview)

工作流可保存为小型 JSON，当前有正式 Workflow v1.0 JSON Schema；生成图片还能嵌入产生它的工作流元数据。[工作流概念](https://docs.comfy.org/development/core-concepts/workflow)、[Workflow JSON v1.0](https://docs.comfy.org/specs/workflow_json)

### 建议适配器合同

新增独立 `comfyui-local` GenerationAdapter，而不是把 ComfyUI 代码并入 Electron：

1. 预检 `baseUrl` 只能是明确允许的 `127.0.0.1/localhost`，读取 `/system_stats`、`/features` 和 `/object_info`。
2. 读取项目内已批准的 API-format workflow，替换白名单输入：提示词、seed、宽高、批次数、参考图路径或已上传文件名。
3. 持久化完整工作流快照、SHA-256、ComfyUI 版本、核心节点定义摘要、模型名和自定义节点清单。
4. 调用 `/prompt` 后立刻保存 `prompt_id`；没有可靠回执时进入 `submission_unknown`，先查 `/queue` 和 `/history`，绝不自动重复提交。
5. WebSocket 只负责实时体验；重启恢复以 `/history/{prompt_id}` 和真实输出文件为准。
6. 下载或复制输出到项目隔离目录，执行魔数、尺寸、可解码、SHA-256、占位图和 raw/labeled 验收后，才登记新素材版本。
7. 用户取消时区分 pending 删除和 running interrupt；没有确认服务器状态前不能把任务写成已取消。

### 可借鉴结构

- “提交完整不可变工作流”比只保存提示词可靠，应成为所有高级生成 Adapter 的统一 provenance 字段。
- 节点级进度可映射到画布的 `preparing / loading_model / sampling / decoding / saving / verifying`，但业务完成仍以落盘验收为准。
- ComfyUI 的缓存/部分执行适合迭代同一镜头；当前应用只登记最终输出，不把缓存命中冒充新素材版本。
- 输出图片中的工作流元数据可作为补充证据，但权威来源仍是生成任务里已保存的工作流快照和哈希。

### 集成成本与风险

- GPL-3.0：不复制、链接或打包 ComfyUI Core；只连接用户独立安装并主动启动的外部服务。是否随应用分发 ComfyUI 必须单独做法律和安装包评估。
- 自定义节点与模型各自可能有不同许可证，且版本漂移会让旧工作流无法执行。必须保存环境快照并在提交前用 `/object_info` 验证节点。
- 本机 ComfyUI 常缺少认证。适配器默认只允许 loopback，不自动开放 LAN，不保存网页 Cookie 或云 API 密钥。
- 官方 Core 发布节奏较快，master 及自定义节点可能破坏兼容性；应固定已验证稳定版，而不是追最新提交。[官方发布说明](https://github.com/Comfy-Org/ComfyUI#release-process)

### 决策

进入当前项目，优先级 P1。先支持一个本机地址、一个已批准工作流目录和图片任务；视频工作流、云 API、自动安装模型与第三方节点均放到后续。首版仍必须在每批视觉验收后暂停。

## 9. 建议实施顺序

### P1：直接提升可靠性

1. `comfyui-local` 外部适配器：工作流快照、`prompt_id`、队列/历史对账、WebSocket 节点进度、隔离验收。
2. 统一 `PublicationIntent`：预检输出路径、版本预留、幂等键、生成/渲染完成后的最终注册。
3. 视频审片时间码与坐标批注，继续绑定不可变素材 ID 和 SHA-256。
4. 剪辑异常退出恢复选择器，不改变现有持久撤销栈。（已完成）

### P2：有限试验

1. Revideo 内置包装模板适配器。
2. 严格门禁的 Lossless FFmpeg 快速导出。

### P3：有真实协作需求再做

1. Kitsu/Zou 外部连接器。
2. OpenAssetIO Python sidecar Manager 或第三方 Manager 互操作。
3. OpenCut 只有发布稳定 Editor API/Headless API 后重新评估。

## 10. 明确不做

- 不把 Kitsu/Zou 变成当前单机项目的第二事实源。
- 不复制 GPL/AGPL 项目的核心代码、UI 或数据层进当前应用。
- 不用 OpenCut 的路线图替代已实现的编辑、MCP 和恢复功能。
- 不把 Revideo 的回调接口误当可靠持久队列。
- 不因 ComfyUI WebSocket 显示 `executed` 就宣布素材完成；必须完成输出落盘和机械验收。
- 不允许任何 Adapter 覆盖权威素材或用缓存/预览图冒充新版本。
