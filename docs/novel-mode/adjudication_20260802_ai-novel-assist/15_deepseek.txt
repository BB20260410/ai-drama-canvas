A. 一句话结论  
当前 Writing OS V1 已把“正文 CAS + 人物状态投影 + 写前指纹锁定”做成机械闭环，能阻止最粗暴的模型漂移与篡改，但仅靠它无法支撑 100 万字跨模型人物一致性——因为它缺失**状态自动演进、知情强制约束、多代理接力协议与长程漂移巡检**。画布必须补上“可视化控制台 + 一致性监察引擎”，让模型真正靠系统写，而不是靠聊天记忆硬扛。

B. 当前能力 vs 真实写作痛点（表）  

| 当前能力 | 真实写作痛点 | 缺口 |
|---------|------------|------|
| 每章截止状态投影（writing-state） | 百万字后人物外形、声口仍会缓慢漂移，因为状态更新依赖人工且非实时 | 无自动漂移检测与状态修正建议 |
| 知情记录（谁知道了什么） | 模型经常无意中让角色说出未知信息，审稿票无法在生成前阻止 | 无写前知情违规拦截器 |
| 八项动态状态候选 + 人工 commit | 长程中状态累积过多，人工审核成本巨大，易遗漏 | 无状态自动演进引擎，无法从正文自动提取变化 |
| 跨章 revision/SHA 一致性 | 多模型接力写时，若模型 A 的风格/声口与模型 B 不同，后期融合困难 | 无角色声口/风格特征库与一致性约束 |
| 审稿票只读 | 审稿模型只能指出问题，不能强制修改，人工不处理则问题堆积 | 审稿票需与写流程联动，阻塞后续章节 |
| 命令账本与 idempotencyKey | 分布式多 Agent 写入时，可能因网络问题丢失状态推进 | 缺少状态事务与接力上下文锁 |
| 搜索与切片 | 百万字全文搜索性能下降，可能影响上下文包生成 | 无索引优化与分层缓存 |
| 画布仅隔离 pilot | 作者无法直观看到人物关系网、知情时间线、状态变化曲线 | 画布无小说专用可视化面板 |

C. 目标架构（文字组件图）  
- **画布小说控制台**：无限画布上展示人物关系图、知情时间线、章节结构树、状态变化曲线。可拖拽分配任务给不同 AI 模型。  
- **MCP 服务层**：现有只读工具 + 新增一致性检查、状态演进、接力协议接口。  
- **Writing OS 核心**：  
  - CAS 存储（正文 + 状态 + 来源对象）  
  - 写作状态机（每章 preflight / pack / commit）  
  - **一致性监察引擎**（新增）：预写时检查知情、声口、外形、禁揭；写后漂移扫描。  
  - **状态自动演进器**（新增）：从新建正文中提取八项状态变化，生成候选，减轻人工。  
  - **多代理任务分配器**（新增）：管理章节写锁、模型指定、上下文接力。  
- **命令账本**：记录所有写入，保证幂等与恢复。  
- **人物特征库**（新增）：记录每个角色的外形、声口、习惯、禁忌特征，作为一致性基线和约束输入。

D. Top 10 产品改进（P0/P1/P2）  

P0（必须做，否则百万字必崩）  
1. **知情违规实时拦截**：在 preflight 阶段注入“知情边界检查”，模型输出的正文若包含角色不该知道的信息，直接拒绝保存并提示违规片段。验收门：100 字以上违规片段检出率 > 95%。  
2. **状态自动演进引擎**：从 AI 写完的正文中 NLU 提取八项状态变化，生成 state change candidate，与人工候选并行。验收门：状态变化召回率 > 85%，准确率 > 70%（人工可纠正）。  
3. **多模型写锁与接力协议**：同一时刻仅一个模型可写某章，写完后释放锁并传递上下文签名给下一个模型。上下文签名包含状态截止章、声口特征、未完成伏笔。验收门：接力传递后下一章 preflight 可用，上下文不丢失。  
4. **人物特征库与声口约束**：为每个角色定义外形描述、典型句式、禁用词、语气参数，作为 context pack 必带项，并在 preflight 做风格一致性打分。验收门：同角色跨章声口相似度 > 0.8（基于向量）。  

P1（强烈建议，显著提升质量）  
5. **画布小说控制台（人物/时间线/关系面板）**：可视化知情时间线、关系变化、状态波动，支持人工直接调整候选状态。验收门：人工可在一分钟内定位任意角色的知情变化。  
6. **长程漂移扫描**：定期对百万字全文扫人物外形、声口、关系进度，生成漂移报告，标记需修正章节。验收门：扫描 100 万字耗时 < 5 分钟，定位漂移点。  
7. **审稿票强制闭环**：审稿票关联章节，若未人工确认或未驳回，该章状态不得 commit，阻塞后续章节。验收门：审稿票未处理时，后续章节 preflight 返回 `review_ticket_pending`。  
8. **上下文包分层缓存**：对于未变化的章节与状态，缓存 context pack 构建结果，仅增量更新，加速百万字级 pack 生成。验收门：百万字续写 pack 构建时间 < 2 秒。  

P2（锦上添花）  
9. **模型专属适配器**：对不同模型（Grok/Claude/千问等）输出格式、声口进行微调适配，确保一致性。  
10. **多分支试验与合并**：允许在画布上分出平行章节试验，满意后合并回主线，合并时检查一致性。

E. 人物一致性机械门清单  
1. **外形描述强制继承**：每个角色在 writing-state 中存有“当前外形描述”，写前必须包含，且 preflight 检查正文中是否出现矛盾描述（如发色突然改变）。  
2. **声口指纹**：提取角色典型句式、语气词、句子长度分布，生成声口指纹，preflight 检查新正文文本声口与指纹的余弦相似度，低于阈值警告。  
3. **知情边界硬约束**：知情状态记录每个角色知道的信息条目（如“A 知道 B 是凶手”），preflight 将正文中每个角色的对话/内心独白与知情集比对，发现违规即阻断。  
4. **关系进度锁**：关系状态（如“A 与 B 已离婚但未公开”）在 cutoff 前锁定，写章时不得反向推进，除非状态候选明确变更。  
5. **八项状态变更一致性**：八项（健康、位置、情绪、目标、压力、知识、社会地位、资源）每次变更必须经过“状态候选 commit”，否则视为未发生，后续章节不可引用。  
6. **禁揭清单**：作者可设定“永远不能揭露的秘密”，preflight 检查正文是否包含该秘密，有则直接拒绝。  
7. **跨章引用验证**：若正文引用前文事件，系统自动搜索原文，验证引用是否准确，偏移则提示。  
8. **时间线连续性**：日历状态记录每章发生时间，新章时间必须晚于或等于前章，且不能出现跳跃未说明。  
9. **伏笔追踪**：伏笔条目记录“埋下章节”和“预期揭晓章节”，preflight 提醒作者伏笔是否过期或遗忘。  
10. **多模型一致输出格式**：所有模型输出正文必须符合统一 Markdown 模式，禁止模型自行添加元数据或状态变更说明，强制走状态候选通道。

F. 百万字不崩的工程门（规模/锁/恢复）  
- **规模**：  
  - CAS 分片：正文按章存储，manifest 索引，避免单文件过大。  
  - writing-state 采用增量日志，仅保存变更，全量状态由日志重放，减小文件体积。  
  - 搜索索引：使用倒排索引，支持增量更新，保证百万字搜索 < 500ms。  
- **锁**：  
  - 章节级写锁：通过命令账本实现乐观锁，写前检查 expectedRevision 和状态 cut，冲突则拒绝。  
  - 状态事务：stage 状态候选和 commit 作为原子操作，防止并发污染。  
- **恢复**：  
  - 断点恢复：每章写完自动保存状态快照（writing-state + context pack fingerprint），重启后可从最后接受状态继续。  
  - 幂等重放：所有命令携带 idempotencyKey，账本记录，重复请求返回原结果。  
  - 灾难恢复：正文 CAS 与状态文件分布式备份，可随时从 manifest 重建工程。  
  - 百万字长程验证：定期全量校验正文 SHA 与 manifest 一致性，检测静默损坏。

G. 多 AI 协作协议（谁写/谁审/谁改状态）  
- **写手模型**：按章节分配，任务来源于画布上的任务卡片（指定模型、章节、目标）。强制走完整 pack → preflight → save → stage 候选流程。写完后提交状态候选，并自动生成审稿票给审稿模型。  
- **审稿模型**：自动接收审稿票，检查一致性、知情、文笔，生成 review ticket（只读）。审稿票可包含“建议修改”但不得直接改文。人工可决定是否采纳并触发修改。  
- **状态修改者**：只能是人工（通过画布）或状态自动演进引擎（生成候选），但最终需要人工 commit。不允许 AI 直接修改正典状态。  
- **接力协议**：  
  1. 当前写手完成章节并状态 commit 后，系统生成“接力上下文包”，包含：截止章状态、声口特征、未完成伏笔、禁揭清单、下一章细纲。  
  2. 下一写手（可能不同模型）通过 `get_novel_writing_state` 获取接力上下文，并开始新章。  
  3. 若更换模型，系统自动注入该模型所需的风格适配 prompt。  
  4. 任一写手发现前文矛盾，可提交“矛盾报告”，强制人工介入，不自动覆盖。  
- **协作约束**：同一章不可同时分配两个写手；审稿模型可并行工作，但审稿票需按章节顺序处理，防止状态混乱。

H. 明确「软件做不到 / 不该做」  
- 软件不做文学判断：不评价“文笔好坏”“情节是否精彩”，仅提供一致性机械约束。  
- 软件不替代作者创意：不自动生成剧情、人物弧光，仅提供状态追踪和漂移警报。  
- 软件不保证零错误：即使所有机械门通过，仍可能出现逻辑漏洞，最终责任在作者。  
- 软件不强制写作风格：声口指纹仅作为参考，作者可覆盖。  
- 软件不在无人工干预下自动修改正典：所有状态变更需人工 commit，自动演进仅生成候选。  
- 软件不承担跨作品知识迁移：不同小说间的人物、设定不互通，需独立配置。

I. 90 天路线图  
- 第1–15天：实现知情违规拦截器（P0-1）与人物特征库基础（P0-4），集成到 preflight 流程。  
- 第16–30天：完成状态自动演进引擎（P0-2）与多模型写锁接力协议（P0-3），单机测试连贯性。  
- 第31–45天：画布小说控制台最小可用版（P1-5），显示人物关系、知情时间线，并支持状态候选人工调整。  
- 第46–60天：长程漂移扫描（P1-6）与审稿票强制闭环（P1-7），接入百万字测试《黑页》试跑。  
- 第61–75天：上下文包缓存与性能优化（P1-8），保证百万字流畅。  
- 第76–90天：集成多模型适配器（P2-9），完成整个闭环，输出 SOP 文档，交付评审。  

验收门：90 天后，用《黑页》100 万字真实工程，连续 50 章由至少两个不同模型接力写作，人物一致性漂移率（人工评估）低于 5%，无知情违规，状态自动演进准确率 70% 以上。
