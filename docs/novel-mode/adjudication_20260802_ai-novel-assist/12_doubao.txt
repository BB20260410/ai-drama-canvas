# A. 一句话结论
现有Writing OS V1是百万字多AI写作一致性的必要流程底座但远不充分，必须在不推翻既有CAS/命令总线架构、复用漫剧BindingSet能力的前提下，补全**结构化人物基底、写后机械扫描、分片状态投影、画布裁决驾驶舱、多代理权限隔离**五大核心能力，才能让Grok/Claude等模型完全靠系统提供的带指纹上下文写作、不靠聊天记忆硬扛，实现百万字人物不崩、多代理可接力、故障可恢复；软件仅提供机械门，文学判断与最终裁决权100%归人类作者。

---

# B. 当前能力 vs 真实写作痛点
| 当前已有能力（V1已落地） | 百万字多AI写作真实痛点 | 核心缺口 |
|---|---|---|
| 正文CAS+manuscript版本、单章写入幂等、命令账本 | 1. 修改早期待后，后续章节与正典冲突无感知；2. 多代理同时写同一章/改状态易出现覆盖；3. 故障后无法快速定位正确接力点 | 无跨章影响锁、旧章修改审批流、不可变接力点机制 |
| writing-state八项动态、状态候选人工commit | 1. 人物不可变基底（外形、声口、永久禁揭、核心动机）散落在正文/设定里，跨模型解读不一致；2. 动态状态与基底无绑定，容易出现设定漂移；3. 单一state文件随章节膨胀，读取/校验性能指数级下降 | 无结构化不可变人物BindingSet、状态与基底SHA绑定、状态分片增量投影 |
| Context Pack 2.0+preflight写前校验 | 1. 仅校验上下文是否最新，不校验生成正文是否符合状态/硬设定，模型写崩（如死人复活、知情越界）系统无感知；2. 硬正典内容可被预算裁剪/被模型篡改，无独立校验 | 无写后一致性机械扫描、硬正典段独立指纹防篡改 |
| 审稿票绑定正文区间、状态候选 | 1. 人审需翻JSON、上百章正文找证据，单章审核耗时超10分钟，百万字下完全不可行；2. 冲突无分级，critical问题容易被淹没 | 无可视化状态diff/冲突聚合面板、审稿票锚点一键跳转、冲突分级拦截机制 |
| 多模型可通过MCP接入、JSON CLI兼容 | 1. 无角色权限隔离，写手可越权改状态、审稿可越权改正文；2. 模型可依赖自身聊天记忆/外部知识写作，系统无法约束；3. 跨模型接力时上下文无统一可信来源 | 无多代理角色权限固化、身份全链路追溯、接力点强制拉取机制 |
| 1M/500章导入smoke测试PASS | 仅验证导入不崩溃，未验证长期写作下的状态一致性、损坏恢复、性能稳定性，无长期SLA | 无全量定期一致性校验、CAS分片损坏重建、长程压测门禁 |
| 漫剧侧已落地BindingSet/连续性驾驶舱 | 小说侧与漫剧侧数据模型不同构，无法复用已验证的一致性能力，重复开发成本高 | 小说侧未对接BindingSet体系、无专属一致性驾驶舱 |

> **尖锐判断：仅靠现有Writing OS V1，最多支撑10-20章的短篇单代理写作，完全无法支撑百万字跨模型人物一致性——核心是它只管住了「写入流程合法」，没管住「写入内容合规」；只管住了「单章状态」，没管住「全局人物锚点」；只管住了「机器存储」，没管住「人类裁决效率」。**

# C. 目标架构（文字组件图）
```
[人类作者] <--> [画布UI层] <--> [命令总线/CAS存储层] <--> [MCP服务层] <--> [多模型代理层]
```
## 各层职责与接口形状
### 1. 画布UI层（人类唯一操作入口，复用漫剧P0-P14已关账组件）
- 新增小说模块：人物BindingSet编辑器、一致性驾驶舱、状态候选diff审批面板、伏笔/禁揭时间线、审稿票聚合中心、多代理权限管理页、旧章修改审批流
- 核心规则：仅做人类操作的可视化与输入，不直接生成内容给模型；所有写入经命令总线落CAS；不存储任何私有状态，所有视图均从CAS投影
- 漫剧兼容：BindingSet数据模型兼容生图侧，小说扩展字段（声口样本、知情边界）使用独立命名空间，不影响漫剧已有功能

### 2. 命令总线/CAS存储层（唯一真相源，完全兼容V1合同）
- 不可变CAS对象：正文分片（按章）、人物BindingSet分片（按角色）、Writing-state逻辑根manifest+状态分片（按角色/关系/时间线/伏笔）、命令账本、审稿票、接力点快照
- 核心规则：不引入任何数据库，所有数据为项目内普通文件；原`story-bible/writing-state.json`改为逻辑根manifest，物理分片对外仍呈现为单一逻辑状态，兼容V1接口
- 新增CAS类型：`character-binding/<characterId>-<sha256>.json`、`relay-point/<chapterId>-<sha256>.json`、`state-shard/<domain>-<characterId?>-<sha256>.json`

### 3. MCP服务层（模型唯一访问入口，零信任）
保留V1所有接口，新增3个只读工具、3个可写命令：
```typescript
// 只读工具
// 获取指定版本的人物BindingSet
get_novel_character_binding: (params: {
  projectRoot?: string, characterId: string, bindingSha?: string
}) => {
  binding: {
    id: string, sha256: string,
    immutableTraits: Record<string, any>, // 结构化外形硬约束
    voiceSamples: {chapterId: string, range: [number, number], text: string}[], // 声口样本
    permanentForbiddenReveals: {secretId: string, description: string}[],
    coreMotivation: string
  },
  version: number
}

// 写后一致性扫描，返回分级冲突
scan_novel_chapter_consistency: (params: {
  projectRoot?: string, chapterId: string, revision: number, contentSha256: string
}) => {
  criticalConflicts: {ruleId: string, characterId?: string, range: [number, number], message: string, evidence: string}[],
  warningConflicts: {ruleId: string, characterId?: string, range: [number, number], message: string}[]
}

// 获取最新可信接力点
get_novel_relay_point: (params: {projectRoot?: string, targetChapterId?: string}) => {
  relayPointId: string, chapterId: string, revision: number,
  allCasShas: Record<string, string>, contextPackFingerprint: string,
  preflightId: string, stateDiffSummary: string
}
```
```typescript
// 可写命令（均走execute_command，带权限校验）
// 批量导入人物BindingSet（仅人类画布可调用，AI无权限）
novel_seed_character_bindings: (payload: {
  bindings: Omit<CharacterBinding, "sha256" | "version">[]
}) => {seededCount: number, bindingShas: string[]}

// 申请状态override（如死人复活，仅状态整理代理可提交，人工审批）
novel_stage_state_override: (payload: {
  candidateId: string, reason: string, evidenceRanges: [number, number][],
  targetStateShard: string, expectedBaseSha: string
}) => {overrideCandidateId: string}

// 审批旧章正典修改（仅人类可调用）
novel_approve_canon_revision: (payload: {
  chapterId: string, targetRevision: number,
  impactReport: {affectedChapterIds: string[], conflictCount: number}
}) => {approved: boolean, newRelayPointId: string}
```

### 4. 多模型代理层
- 所有模型（Grok/Claude/Codex/千问/豆包/GLM等）仅能通过MCP访问，无文件系统直接权限
- 所有请求携带`agent_id`、`agent_role`，全链路可追溯

> **画布与MCP核心分工**：MCP是模型的「紧箍咒」，负责卡机械规则、喂最小可信上下文、拒绝违规写入，绝不给旁路；画布是人类的「裁决台」，负责把状态、冲突、证据可视化，让人类1分钟内完成单章审批，绝不让人翻JSON找证据。

# D. Top 10 产品改进（P0/P1/P2）
## P0（90天内必须交付，不做无法支撑百万字MVP）
### 1. 结构化人物BindingSet CAS化（复用漫剧模型）
- 内容：每个出场角色生成独立不可变CAS，包含结构化外形硬约束、3-5段带出处的声口样本、核心动机、永久禁揭清单、不可变基础关系；writing-state仅存动态增量并引用BindingSet SHA；未绑定BindingSet的角色出场时preflight直接失败
- 接口：新增`get_novel_character_binding`、`novel_seed_character_bindings`；扩展Context Pack，硬正典段首位放目标角色BindingSet，不可裁剪
- 验收门：未seed BindingSet时preflight返回`binding_required`；硬正典预算不足时直接报错，不裁剪BindingSet
### 2. 写后一致性机械扫描引擎
- 内容：正文save后、stage状态候选前自动扫描4类critical冲突：人物状态冲突（已死/不在场无变更出场）、知情边界越界、禁揭提前触发、外形硬约束冲突；critical冲突直接阻断状态候选，自动生成带正文锚点的审稿票
- 接口：新增`scan_novel_chapter_consistency`；扩展`novel_save_chapter`返回值带扫描摘要
- 验收门：10个标准冲突用例检出率100%；有critical冲突时无法提交状态候选
### 3. Writing-state分片投影重构（兼容V1）
- 内容：原单一state文件改为逻辑根manifest，物理上按「角色状态/全局关系/时间线/伏笔」4域拆分CAS分片；`get_novel_writing_state`对外仍返回完整逻辑视图，按需拼接
- 接口：完全兼容V1，无breaking change
- 验收门：500章/100万字下state读取p95≤200ms，pack生成p95≤1s；单分片≤1MB；旧工程无缝升级
### 4. 小说一致性驾驶舱（复用漫剧组件）
- 内容：展示角色BindingSet版本、八项状态、知情边界、关系进度、出场热力图、禁揭清单；状态候选diff红绿对比，点击直接跳正文；审稿票按等级聚合
- 验收门：单章状态审核耗时≤1分钟，无需打开任何源文件；漫剧已有功能无回归
### 5. 硬正典独立指纹校验
- 内容：Context Pack拆分为「不可裁剪硬正典段」（BindingSet、禁揭、章纲、上一章最终状态）和「可裁剪证据段」；硬正典生成独立子指纹，preflight和save时必须校验
- 接口：扩展pack返回`hardCanonFingerprint`；save时必须携带该字段
- 验收门：篡改硬正典的请求100%返回`hard_canon_fingerprint_mismatch`

## P1（90-180天交付，提升多代理效率与长程稳定性）
### 6. 多代理权限隔离与全链路追溯
- 内容：权限固化：写手仅能写正文、审稿仅能附票、状态整理仅能提候选、人类拥有全部审批权；所有操作记入账本
- 验收门：跨权限调用100%被拦截；可按章/代理追溯所有操作记录
### 7. 伏笔/禁揭时间线管理
- 内容：独立伏笔CAS，结构化记录埋设章、回收窗、关联角色；pack自动塞入待回收伏笔、3章内弧光提醒；写后扫描伏笔/弧光偏差
- 验收门：10个伏笔/弧光用例提前/逾期触发100%出告警
### 8. 不可变接力点与跨章stale锁
- 内容：每章commit后自动生成接力点快照；写章前必须拉取最新接力点，否则preflight失败；修改旧章后后续章节接力点自动标记为stale
- 验收门：未拉拉力点的写请求100%被拦截；改第N章后第N+1章及以后preflight自动返回stale

## P2（180天以上交付，优化体验，不影响核心一致性）
### 9. 跨模型一致性基准测试套件
- 内容：内置标准测试集，一键跑所有模型的一致性得分，低于阈值的模型仅能写龙套
- 验收门：6个主流模型得分误差≤5%；低权限模型写主角时被拦截
### 10. 本地声口/风格辅助校验
- 内容：集成本地小模型对比台词与声口样本的相似度，支持自定义风格规则，仅出warning不拦截
- 验收门：声口偏差检出率≥80%，误报率≤10%；无数据外传

# E. 人物一致性机械门清单
## 写前强制门（不满足无法写作，100%机械执行）
1. 所有出场角色必须绑定已审核的BindingSet，SHA与state引用一致
2. 硬正典段完整、指纹校验通过，未被裁剪
3. 上一章状态候选已人工commit，接力点为最新
4. 代理拥有对应角色的写作权限
5. 目标章的结构化禁揭、知情边界已完整加载
## 写后硬拦截门（不解决无法进状态候选，100%机械执行）
1. 人物状态冲突：已死/不在场/被限制角色无变更出场
2. 知情边界越界：角色说出自己cutoff下不知道的结构化秘密
3. 禁揭触发：在允许章节前提及结构化禁揭内容
4. 外形硬约束冲突：与BindingSet结构化设定矛盾且无变更候选
5. 硬正典指纹不匹配
## 写后警告门（仅生成审稿票，供人参考）
1. 声口相似度低于阈值
2. 人物行为与核心动机有明显偏差且无铺垫
3. 关系进度突变无对应状态候选
4. 弧光checkpoint未达标/提前触发
5. 伏笔逾期/提前回收
## 人工最终裁决门（软件不做判断）
1. 所有warning级冲突的取舍
2. 状态override申请（如死人复活、时间线调整）
3. 文学性人物塑造调整（不碰硬约束）
4. 非结构化禁揭/伏笔调整
5. 旧章正典修改审批

# F. 百万字不崩的工程门
## 规模门
1. 所有CAS按域分片：正文单章建议≤2万字，状态单分片≤1MB，无超大文件
2. Context Pack默认预算60k字符，硬正典占比≤30%，超预算直接报错不静默裁剪
3. 所有读操作分页：章节列表limit≤500、正文单次读≤20万字、搜索单章命中≤20条
4. 投影层按「cutoff章+角色+任务类型」缓存，命中率≥90%，500章下读操作p95≤500ms
## 锁门
1. 章节写锁：同一时间仅一个主体可改同一章，锁绑定幂等键，超时15分钟自动释放
2. 状态候选锁：同一时间仅一个待审核候选
3. 接力点stale锁：旧章修改后后续章节必须重新同步接力点
4. 正典修改锁：已commit超30章的旧章修改必须人工审批，自动生成影响报告
## 恢复门
1. 命令账本幂等：中断后用原幂等键重试，无重复写入
2. 接力点快照：每章commit后自动生成，支持一键回滚
3. 外部变更检测：读前校验磁盘与manifest SHA，不一致时提示人工合并，不覆盖
4. 分片重建：单个CAS损坏时自动从账本和接力点重建，校验失败则告警
## 验证门
1. 每日全量一致性扫描，生成冲突报告
2. 每100章自动跑多代理接力压测，不通过禁止上线
3. 外部工程导入时自动扫描冲突，冲突率高于5%提示人工整理

# G. 多AI协作协议
## 角色定义（权限固化在MCP层，不可自行修改）
1. **写手代理**：仅能写正文，必须完整使用系统返回的preflight参数，不得用聊天记忆当依据；无状态/审稿权限
2. **审稿代理**：仅能提交绑定证据区间的审稿票，不得改正文/状态，不得提无依据的泛泛意见
3. **状态整理代理**：仅能基于正文内容提取状态变化、提交候选，不得添加正文无依据的设定；无正文写入权限
4. **人工Owner**：唯一裁决者，拥有所有审批权，负责最终确认状态、裁决冲突、修改设定
## 绝对禁止模型自由发挥的领域（机械拦截）
1. 禁止修改人物BindingSet的不可变字段、自行调整禁揭/知情边界
2. 禁止直接提交状态为正典，所有变更必须人工审批
3. 禁止裁剪/篡改硬正典段、绕过preflight写入
4. 禁止修改已commit超30章的旧章，除非人工审批
5. 禁止跨权限调用、冒用其他身份
6. 禁止将聊天记忆、外部知识作为正典依据，所有设定必须来自CAS上下文

# H. 软件明确做不到/不该做的
1. **不保证文学质量**：不判断文笔、故事、人物塑造的优劣，完全由人负责
2. **不做创造性决策**：不主动生成剧情、设计伏笔、调整弧光，仅执行人类设定的规则
3. **不替代人工审核**：所有冲突裁决、状态审批必须人来，软件仅提供证据
4. **不支持无结构化设定的写作**：不整理BindingSet、不设禁揭/章纲时，仅能当普通编辑器用，无一致性保证
5. **不阻止作者主动写崩**：人工确认的设定变更（如死人复活），软件仅记录不拦截，崩了作者负责
6. **不保证模型输出质量**：未触发机械冲突的垃圾内容、逻辑漏洞，由人/审稿代理把关
7. **不跨项目复用设定**：每个项目的正典完全独立，除非手动导入
8. **不认可聊天记忆**：聊天记录仅为临时会话，不算正典，系统不会从中提取任何设定
