## 0. 主审一句话（直接答你的问题）

**能。** 无限画布**可以**成为 Grok / Codex / 千问 / 豆包 / GLM 等写小说的「一致性操作系统」——但**不是今天这版 UI**，也**不是**「再接几个模型」。

- **今天**：Writing OS V1 已经能管住「基于哪个状态、以什么指纹、把哪一章写进 CAS」——**程序一致性**有了。  
- **还不够**：管不住「写出来的人还是不是那个人」——**语义一致性**（外形/声口/知情/禁揭/伤势道具）缺机械门。  
- **百万字**：正文存、有界读、1M/500 smoke **可证**；长程不漂要靠 **Cast 硬锁 + 写后扫描 + 状态裁决台 + 章租约 + 状态分片**，不是靠聊天记忆。  
- **画布的真正价值**：把模型降格为「候选生成器」，把人抬成「正典裁决者」；让任何 AI **只能**走同一套 pack → preflight → save → 状态候选，**不能**各写一份 MEMORY 当真源。

**假承诺禁止**：软件不能保证文笔、不能 0 人工自动永不漂、不能拦模型用外部知识瞎编——只能限制**注入上下文**、**拒绝脏写**、**事后对照清单**、**强制状态 commit**。

## 1. 五轨 + 五模共识（高度一致的点）

| 共识 | 出处 |
|---|---|
| V1 强在写入门、弱在输出门（管手不管笔） | 全席一致 |
| 未指定 cast 时角色可被 pack 预算静默裁掉 = 最大一致性洞 | 一致性子代理 + 代码事实 |
| NovelStudio 仍是编辑器，MCP 才是 OS → **人机分裂** | 缺口审计 + 产品轨 |
| 小说写路径无生图级 write lease | 多 AI 轨 + 规模轨 |
| 单文件 writing-state 在稠密年表会爆 | 规模 + GLM/千问 |
| 禁揭/知情/声口/伤势道具缺一等结构或机审 | 全席 |
| 状态 commit 必须人工；自动 accept 是有害方向 | 全席 |
| 先做驾驶舱 + Diff 裁决台，再谈智能抽取 | 产品 + 缺口 |

**分歧与主审裁决**

| 分歧 | 主审裁决 |
|---|---|
| 写后扫描要不要挡 save | **P0 默认出 ticket 不挡 save**；`mustNotDo`/禁揭命中可升 **block_save**（可配置） |
| 状态自动抽取 | **P1 建议引擎**，召回优先、准确率人工改；禁止自动 commit |
| writing-state 立刻分片 | **S1 不必**；红线：文件 >8MiB 或 knowledge>100k 或 load p95>200ms 才拆 |
| FTS | **P1**，规范已写未实现；S1 线性搜可用但非 SLA |

## 2. 目标架构（文字）

```
人类 Owner（唯一正典推进权）
    │  驾驶舱：STATUS 水位 / 状态债 / 禁揭灯 / 租约 / Diff 裁决
    ▼
编排 Agent（Grok 等）—— 只调度，不主笔正文
    │  acquire 章租约 · 派工 · 检查 pending candidate
    ▼
主笔 / 结构审 / 声口 / 探针  ──一律──►  MCP / JSON CLI
    │                                      │
    │         Context Pack 2.1             │
    │         (Cast 强制 + 声口/外形硬槽)   │
    │         preflight + 可选 lint        │
    │         novel_save + aiWriteContext  │
    │         stage candidate / review票   │
    ▼                                      ▼
唯一真相：manuscript CAS + writing-state CAS + Binding/Cast 对象
         （禁止聊天记忆、禁止各模型私有 MEMORY 当真源）
```

**UI vs MCP**

| 面 | 职责 |
|---|---|
| MCP | 机器强制门：指纹、cutoff、空章、lease、错误码 |
| 画布 | 人看得见的门：水位、Diff、禁揭、cast 编辑、接力板 |
| 两者必须同构 | preload/IPC 暴露与 MCP 同语义的只读 + 人工裁决写 |

## 3. 人物一致性：要机械化的门（E）

### 3.1 CastBindingSet（对标漫剧 BindingSet）

每角色不可变/慢变槽位（budget **硬装载**，装不下 fail-close）：

- 外形 tokens（疤、发、身高量级…）  
- 声口 anchors（2–5 段真对话引用 + 禁用词/称呼表）  
- 永久禁揭 / 作者 only  
- 核心动机一句话（可 revision，变更要证据）

### 3.2 八项动态 + 知情 + 关系

- 写前：`cutoff=before` 投影强制进 pack（本场 cast 清单必选）  
- 写后：机审四态 — `一致 / 需复核 / 明显漂移 / 无法检查`  
- 知情越权、禁揭命中 → ticket；高危可 block_save  
- 关系/伤势/持有物：补 **object-injury** 一等账（对齐验收 9.1）

### 3.3 错误码建议（摘）

| 码 | 含义 |
|---|---|
| `cast_required` | 本场未指定 cast 或强制角色被裁 |
| `cast_slot_oom` | 硬槽装不下（不是裁正文） |
| `ban_reveal_hit` | 正文命中禁揭 |
| `knowledge_violation` | 角色说出 unknown/planned_later |
| `state_commit_required` | 已有，保留 |
| `novel_write_lease_required` | 无章租约禁止 AI save |

## 4. 多 AI 如何靠同一工程写（G）

| 席位 | 默认模型 | 允许 | 禁止 |
|---|---|---|---|
| 编排 | Grok | 租约、空章、读工具、派工 | 主笔正文 |
| 主笔 | 千问 | save+aiWriteContext、stage candidate | 直接 accept 正典 |
| 结构审 | GLM | review_ticket | save 正文 |
| 声口 | 豆包 | ticket 或窄 revise（另 preflight） | 改 hardCanon |
| 探针/去味 | DeepSeek | ticket | save 正典 |
| Owner | 人 | accept/reject 状态、human_ui 手改 | 把 Agent 设成 human_ui |

**硬规则**

1. 跨模型必须**重走** pack+preflight，禁止复用旧 fingerprint。  
2. 任一 AI 最多写**候选**；正典只经人。  
3. 小说写命令纳入 write lease（现网租约主要在生图）。  
4. 禁止各家 MEMORY/会话笔记进正典目录。

## 5. 百万字不崩：工程门（F）

| 层 | S1（~1M/500 章） | 何时升级 |
|---|---|---|
| 正文 | 章级 Markdown+CAS | 保持 |
| 搜索 | 线性可用（smoke 109ms） | 产品 SLA → FTS `novel-derived` |
| writing-state | 单文件可 | >8MiB / knowledge>100k / load p95>200ms → 分片 |
| 恢复 | 正文 operations+ledger 强 | state 半提交审计加强 |
| 多代理 | CAS 撞车 | **章租约 enforce** |
| 验收 | smoke ≠ SLA | 固定金标 + 漂移回归 + soak |

**结论**：百万字**放得下**；**一致性不漂**取决于 Cast 门 + 状态债清零速度 + 人不绕过驾驶舱。

## 6. Top 10 产品改进（唯一执行表）

### P0（2–4 周 · 不做则谈不上「辅助写小说」）

1. **写作驾驶舱**：`currentThroughChapterId`、completion 水位、stale 灯、`state_commit_required`、下一动作。  
2. **状态候选 Diff 裁决台**：八项/知情/关系/伏笔对照 + accept/reject。  
3. **Cast 强制装载**：本场 cast 必选；硬槽 fail-close；修「未指定可静默省略」。  
4. **堵人类分叉**：人保存正文后状态可能 stale 的**可见灯**（与 Agent 同逻辑）。  
5. **禁揭清单一等结构 + 写后扫描出票**（默认不自动改稿）。

### P1（1–2 月）

6. 外形/声口 Authority 卡（revision+指纹进 pack 硬槽）。  
7. object-injury / 持有物账。  
8. 小说章级 write lease + actor 矩阵 enforce。  
9. preload/IPC 与 MCP 同构暴露 Writing OS 读 + 人裁决写。  
10. FTS + 角色级召回（「某人上次说谎语气」类查询）。

### P2

- 状态自动演进建议引擎（只生成 candidate）。  
- 与漫剧 Binding/连续性同构投影（hybrid 单向：锁小说版本→短剧）。  
- 外部 `tracking/*.md` ↔ writing-state 双向桥。  
- 长程 soak / 金标漂移回归 / 安装版与 current candidate 对齐策略。

## 9. 对你三个具体问题的最终答

### Q1：软件如何真正辅助 Grok/Claude/Codex 写小说？

让它们**永远只做候选**：读同一 pack、过同一 preflight、写同一 CAS；人在画布上裁决状态与禁揭。  
辅助的巨大增益来自：**省掉每轮粘贴全书/角色卡、挡住脏写与过期状态、强制接力协议**——不是替你写出「更好的句子」。

### Q2：如何做到人物一致性？

**机械三件套**：  
1）Cast 硬锁（慢变）+ 八项/知情（快变，人工 commit）；  
2）写前强制装载，写后四态扫描；  
3）跨模型禁止复用旧指纹。  
文学层仍要人审；机器只杀「死人复活 / 不该知道的秘密 / 禁揭字面命中」这类可判定违规。

### Q3：能否用这软件撑 100 万字不崩？

**存储与单章闭环：能（已有 smoke）。**  
**跨模型人物不漂百万字：现在不能；按 P0–P1 做完后可以「工程上可维护」，仍需人审状态债。**  
不崩的定义应是：  
- 任意章可恢复到 SHA；  
- 无 commit 不能续写；  
- 漂移有票有灯；  
- 多代理不抢写；  
而不是「零人工 AI 全自动神作」。
