# A. 一句话结论

当前 Writing OS 保证了「程序一致性」——写之前读的是真源、写之后有人确认——但**不保证「语义一致性」**：它管住了手，没管住笔；百万字人物一致性会崩在三个地方——通用全文搜索召回不到角色级证据、状态候选全靠人盯、生成内容本身没有任何一道机器门。

---

# B. 当前能力 vs 真实写作痛点

| 已有能力 | 真实痛点 | 差距判定 |
|---|---|---|
| preflight 绑定 pack 指纹，漂移即失败 | 防的是「读过期的书」，防不了「读对了书写错了人」 | 管输入不管输出 |
| 八项状态 + 人工 commit | 500 章时 owner 每章审一份 diff，疲劳即放水；候选本身无机器校验 | 人是单点故障 |
| `state_commit_required` 失败关闭 | 能挡住「跳着写」，挡不住「状态债积压后一次性补假账」 | 有闸门无审计 |
| 通用全文搜索 + 有界读取 | 百万字下「林晚最后一次对哥哥撒谎时的语气」这类角色级召回，通用搜索命中率低 | **最大短板** |
| 硬正典 / 禁揭在 state 里 | 禁揭只是「写进了 state」，没有「正文扫到禁词即拒存」的机械门 | 有数据无执行 |
| review ticket 只读、绑证据区间 | 挂了票无人强制处理； ticket 不阻塞状态 commit | 审稿无闭环 |
| 指纹 + 幂等 + 账本 | 多模型都能走同一合同，但各模型上下文窗口不同，pack 预算一刀切 | 合同同构，配给不同构 |
| 1M/500 章 smoke PASS | 一次性冒烟 ≠ 长程 SLA；状态投影若每次从头重算，500 章后 pack 延迟会拖垮接力 | 性能未关账 |

┌─────────────────────────┐      │   ├ 新增：称谓矩阵门       │

# D. Top 10 产品改进

**P0（不做就不要谈百万字）**

1. **角色实体倒排索引 + pack 角色级召回。** 每角色维护：出场章节列表、关键台词区间、外貌描写区间、关系变化点。`build_novel_context_pack` 传 `characterIds` 时优先召回该角色证据，而非通用搜索。验收：500 章语料上「某角色最后一次说 X 类话」召回准确率 ≥90%，pack 构建 <8s。
2. **禁揭机械门。** 每条秘密在 writing-state 里登记：`{secretId, forbiddenTerms[], revealChapterId}`。`novel_save_chapter` 在 `expectedRevision` 校验之外增加一步：目标章 cutoff 在 revealChapter 之前且正文命中 forbiddenTerms → 拒存，报 `secret_reveal_violation` 并附命中区间。纯字符串扫描，零模型参与。
3. **称谓矩阵门。** 维护 `{称呼者, 被称呼者, 称谓, 生效章节区间}`。save 时扫对话称呼，出现矩阵外称谓 → 警告级 ticket；矩阵明确禁止的旧称谓（关系已翻篇）→ 拒存。这是声口/关系一致性里**唯一能纯机械化的部分**，性价比最高。
4. **状态候选机器校验器。** `novel_stage_chapter_state_candidate` 增加自动校验：schema 合法；不得修改硬正典字段；每个 change 必须附本章正文 UTF-16 证据区间且区间内容可反查；八项字段的枚举值合法。机器校验不过 → 候选根本生不成，把 owner 的审查负担砍掉 70%。
5. **增量状态投影 + checkpoint。** writing-state 按「每 50 章一个 checkpoint + 后续 delta」投影，禁止每次从第 1 章重算。验收：500 章规模 `get_novel_writing_state` P95 <2s，并在 CI 里固定为回归门。

**P1（多模型接力的骨架）**

6. **跨厂商强制审稿路由。** 关键章（owner 标记）在状态候选被接受**之前**，必须存在一张不同厂商模型提交的 review ticket 且 owner 已处置。写章模型与审稿模型同厂商 → preflight 拒绝进入 commit 环节。同源自审不算审。
7. **章节级写租约。** `novel_acquire_chapter_lease(chapterId, agentId, ttl)`：同一章同时只有一个 AI 持有写租约；不同章可并行写；状态 commit 严格串行（接受时只允许推进截止章的下一章，现有规则正好兼容）。租约过期自动释放，画布可视化「谁在写哪章」。
8. **声口样本库。** 每角色 5–10 段 CAS 台词样本（owner 人工选定），进 pack；save 后由独立模型 pass 对该角色本章台词打偏离分，超阈值只生成 ticket 不拒存——声口判断**半机械化**，别把文学判断交给字符串匹配。

**P2**

9. **模型能力注册表。** 登记各模型实际上下文窗口与输出稳定性，pack 预算按调用方自动配给；Grok 和千问拿到的 pack 不应是同一份裁切。
10. **恢复演练工具。** `novel_replay_from(chapterId)`：从 checkpoint 重建 state 并 diff 当前 state；`novel_verify_integrity`：全量 CAS/manifest/SHA 体检。每月跑一次演练，不过关即事故。

# E. 人物一致性机械门清单

按「能纯机械」到「必须半机械」排序：

| 门 | 检查内容 | 执行点 | 强度 |
|---|---|---|---|
| 禁揭词表 | 禁词 × cutoff | save 拒存 | 纯机械 |
| 称谓矩阵 | 称呼对 × 章节区间 | save 拒存/警告 | 纯机械 |
| 外形硬属性 | 发色/瞳色/伤疤等关键词冲突扫描 | save 警告 + ticket | 纯机械（宁误报） |
| 八项状态枚举 | 字段值合法性、禁改硬正典 | 候选生成时拒收 | 纯机械 |
| 证据绑定 | 每个状态 change 必须挂正文区间且可反查 | 候选生成时拒收 | 纯机械 |
| 知情边界 | 「角色说出了不该知道的事实」→ 由审稿模型对照知情矩阵，附证据区间 | review ticket，阻塞关键章 commit | 半机械 |
| 声口 | 台词样本对照打分 | 写后 ticket，不拒存 | 半机械 |
| 关系进度 | 「牵手章节早于关系状态允许值」→ 状态字段 + 审稿模型 | 候选校验 + ticket | 半机械 |

铁律：**纯机械门负责拒存，半机械门负责开票，文学判断永远只开票。**

# F. 百万字不崩的工程门

**规模门（CI 固定，回归即失败）：**
- 500 章 / 1M 字：pack 构建 P95 <8s；state 投影 P95 <2s（靠 checkpoint，禁全量重算）；搜索 P95 <500ms；`novel_save_chapter` 含全部 lint P95 <3s。
- 索引层全量重建 <10min，且重建期间只读工具降级可用（读旧索引 + 标明 stale）。

**锁门：**
- 正文写：章节租约（D7）；状态推进：全局串行单写者（沿用「只推进截止章下一章」）；writing-state.json 本身：CAS 乐观锁 + expectedSha，永远不允许多分支合并。

**恢复门：**
- writing-state 每 50 章 checkpoint + 每章 delta 追加，CAS 存证；任意一章可 `replay_from` 重建。
- 启动即 integrity check：manifest/正文 SHA/writing-state 三方对账，不符 → `external_change`，只读模式。
- 崩溃恢复沿用幂等键语义；新增要求：**所有新增 lint 门必须在命令账本落账之前执行**（对齐现有 `context_preflight_required` 的「拒绝不留痕」语义），避免拒存污染账本。
- 每季度一次「灾难演练」：随机删索引、改一章正文模拟外部漂移，验收恢复路径全自动闭环。

# G. 多 AI 协作协议

| 角色 | 谁干 | 权限边界 |
|---|---|---|
| 写章 | 任一模型（Grok/Claude/千问/豆包/GLM） | 走满 pack→preflight→save；不得直写 state；不得自建章纲 |
| 状态提取 | **独立模型 pass**，输入只有「本章正文 + 上一章 state」，禁止读取写章模型的任何上下文 | 只能产候选；候选先过机器校验器（D4） |
| 审稿 | **与写章模型不同厂商** | 只能 `novel_attach_review_ticket`；关键章无票不得 commit |
| 状态 commit | 只有人 | 接受/拒绝；不得手改 state 文件 |
| 正典裁决 | 只有人 | `hard_canon_conflict` 只能人解，软件永不自动合并 |
| 租约/接力 | 软件自动 | 租约过期回收，接力板对人和 AI 只读可见 |

关键设计：**状态提取必须是无记忆的第二 pass**——写章模型对自己「想写什么」有立场，让它提取状态等于让考生给自己批卷。提取器只看正文说事。

# H. 软件做不到 / 不该做

**做不到：**
- 判断「这段写得像不像林晚」的文学层面——声口门只能报警，不能定罪。
- 发现「主题漂移」「伏笔埋了但忘了收」里需要通读全书的判断——伏笔老化只能按章节数提醒，不能判断文学上的「该收了」。
- 在模型上下文窗口之外凭空给它记忆。pack 预算永远是减法，索引只能提高命中率，不能消灭取舍。

**不该做：**
- 永不自动接受状态候选，永不自动合并正典冲突，永不让 AI 直写 writing-state。
- 永不在 pack 里注入聊天记忆、会话摘要等任何非 CAS 来源。
- 永不为了「流畅接力」放宽 `state_commit_required`——状态债宁可堵死，不可赊账。
- 不把审稿模型的结论结构化进正典——ticket 永远是意见，commit 永远是人。

# I. 90 天路线图

**第 1–30 天：把「写错能拦住」补上（D1、D2、D3）**
- 角色实体索引 + 禁揭门 + 称谓矩阵门上线，全部走 save 前 lint、拒存不落账。
- 验收门：用《黑页》副本（pilot，不当正典）回放 20 章，人工注入 10 个禁揭错误 + 10 个称谓错误，拦截率 100%、误报率 <20%。

**第 31–60 天：把「人盯不住」补上（D4、D5）**
- 状态候选机器校验器 + checkpoint 增量投影。
- 验收门：500 章合成语料性能 SLA 全绿并入 CI；owner 审查单章候选的中位耗时较基线下降 ≥50%。

**第 61–90 天：把「多模型接力」跑通（D6、D7、G 协议落地）**
- 章节租约 + 跨厂商审稿路由 + 无记忆状态提取 pass。
- 验收门：百万字演练——三家以上模型（至少含 Grok 与一家国产模型）接力写 30 章连贯剧情，硬一致性违规（禁揭/称谓/状态冲突）为零，状态债全程为零，中途强制杀进程恢复一次不丢字。

**回到特别判断：** 仅靠当前 Writing OS，百万字人物一致性**撑不住**——它是一座只装了「进门安检」的楼，楼里写什么都没人查。补的顺序就是上面的顺序：先补召回（让模型读得到），再补机械门（让错误存不进），最后补接力协议（让人审得动）。画布 UI 只负责把状态债、锁、票亮给人看；MCP 负责所有能机械执行的拒存；凡是需要文学判断的，一律降级为 ticket，这一条不许讨价还价。
