## 直接回答

### 这些软件的代码对 Codex/AI 有用吗？

**有用，但不是“读了代码，AI 以后就自动记得 100 万字”。**

模型阅读外仓源码不会获得永久记忆，也不会自动改变 Canvas 的运行行为。它们对 AI 的真正帮助是：

1. 为 Canvas 提供已有实现证据的设计模式；
2. 把这些模式 clean-room 重建为可执行合同、状态机、回执和测试；
3. 以后 Codex/Grok/其他 AI 通过 Canvas 取得同一份 cutoff 作业包，且所有写入被 CAS 与人工所有权约束。

所以“代码对我有用”的精确意思是：它们能帮助我更好地设计和验收 Canvas，不能取代 Canvas 把长篇记忆落盘。

### 它们的架构值得借鉴吗？

**值得选择性借鉴，不值得整体迁入。**

最值得学的五类东西：

1. AI-Novel-Writer 的索引代际、冻结快照/outbox、安全发布与项目租约；
2. NovWr 的 durable run、claim/lease/stale reclaim、index freshness 与建议依赖事务；
3. InkOS 的 plan/compose/writer 分层、rule override 和 context trace；
4. MuMu ddys 的知识获得来源、因果链、叙事承诺截止/最近激活概念；
5. probable OCNovel 的中文网文质检分类和可配置检查步骤。

最不值得学的五类东西：

1. 第二套数据库/文件正典；
2. LLM 分析后自动 settle 角色、知情、关系、时间线或伏笔；
3. 只靠近三章、尾部摘要、向量片段和“请保持一致” prompt；
4. 用固定动作词、对话比例、段落长度当所有题材的强制文学门；
5. 从 README 功能表推导实际稳定性。

### 它们能否让 100 万字任务保持一致？

**不能单独保证。Canvas 当前方向是对的，但仍应保留 `VERIFIED_WITH_PERFORMANCE_RISK` 级别的边界，直到完成派生索引、崩溃对账和长压测。**

Canvas 已经有保持一致性最重要的闭环：

`cutoff 正典/状态投影 → Context Pack → preflight → write lease → revision/SHA/fingerprint CAS → 证据候选 → 人工状态接受 → probe/rebuild`

外仓没有一个整体超过这条链。但当前还有两个源码级可证明的 P1 风险：

- 受管章节搜索仍是全文线性扫描；
- 长篇外模任务若在 `executing/submitting` 持久化后进程突然崩溃，没有 TTL/heartbeat/过期对账转换。

Pack 选择轨迹则是第三个 P1 可用性增量：它不改变一致性数学合同，但会显著降低其他 AI 误用 Context Pack 和人类无法定位省略原因的概率。
