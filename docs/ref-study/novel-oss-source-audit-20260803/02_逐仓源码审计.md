# 逐仓源码审计

## 1. InkOS

### 它真正是什么

InkOS 是真实的 TypeScript monorepo，由 `packages/core`、`packages/cli`、`packages/studio` 组成，而不是单一 prompt 壳。Core 同时供 CLI、Studio 和 Agent 使用，这个“一个内核，多个入口”的方向是正确的。

关键源码：

- `packages/core/src/agents/composer.ts`
- `packages/core/src/models/input-governance.ts`
- `packages/core/src/utils/context-assembly.ts`
- `packages/core/src/agents/writer.ts`
- `packages/core/src/utils/atomic-file-set.ts`
- `packages/core/src/pipeline/chapter-persistence.ts`

### 真正值得学的部分

1. **Planner / Composer / Writer 分层**：Composer 先把任务、上下文、规则栈和轨迹组成明确输入，Writer 不自己临时猜该读什么。
2. **规则层级和 override edge**：哪层可以缩窄哪层、哪层不得覆盖 author intent/hard fact，有机械规则，不只是 prompt 口号。
3. **Context trace**：记录 planner/composer 输入、selected sources、protected/compressible 层、token budget 与压缩结果，非常适合借鉴到 Canvas 的 pack 解释面。
4. **正文生成与状态结算分步**：Writer 生成创作文本，另一个低温度步骤产出 state delta，避免一次输出同时承担文风和结构化结算。
5. **文件组原子 helper**：`atomic-file-set` 有 staging、backup、rename 与失败回滚，说明作者有认真处理崩溃边界。

### 不能直接学的部分

- 它以 `story/state/*.json` 等自己的 truth files 为正典 owner，接入 Canvas 会造成第二个正典。
- Writer 的 state settlement 在管线里自动发生；`manual review` 主要是跳过自动审改，不等于 Canvas 的状态 candidate + human accept。
- 有 `commitAtomicFileSet` 并不表示所有写章路径都是整体事务；`chapter-persistence.ts` 对 chapter、truth、index、snapshot 仍是顺序持久化。
- AGPL-3.0 代码不复制、不链接进 Canvas runtime。

### 裁决

`ADAPT_TRACE_AND_POLICY_ONLY`

学 context trace、override policy、创作/状态职责分离；拒绝它的 truth owner 和自动 state settle。

## 2. AI-Novel-Writer

### 它真正是什么

这是 Electron + React + TypeScript 桌面应用，主进程明确拆分 controller/repository/service/security/LLM/MCP，持久化采用 better-sqlite3 和 LanceDB。其工程完整度明显高于普通 AI 写作 UI。

关键源码：

- `electron/repositories/finalization-repository.ts`
- `electron/services/manuscript-publisher.ts`
- `electron/services/project-access.ts`
- `electron/vector-store.ts`

### 真正值得学的部分

1. **Finalization + outbox 同事务**：冻结正文 snapshot/hash/revision/target，在同一 SQLite transaction 更新正文、draft finalized 和 outbox。同快照重放幂等，不同快照拒绝静默替换。
2. **安全发布投影**：Publisher 只读 outbox 冻结内容，在目标同目录独占创建临时文件后 rename。已有同内容视为响应丢失后的幂等重放，不同内容禁止覆盖。
3. **ProjectAccess 租约**：manifest project ID、realpath、active session lease 与当前 DB root 联合授权，并拒绝磁盘根、用户主目录和假同名数据库。
4. **索引代际**：canonical chunks 与 embedding generation 分开；代际身份包括 model fingerprint、dimension、metric。新代际在完整覆盖和 query probe 前不切 active，模型不匹配时安全降级 FTS。

### 对 Canvas 的实际价值

当前 Canvas `NovelRepository.searchChapters` 会读取所有 allowed chapter 并用 `String.indexOf` 扫描。这条路径有 manifest 修订复验、外部变更跳过和 bounded result，但没有持久化派生索引。AI-Novel-Writer 的 generation 协议正好补这个真缺口。

可学的是协议形状：Canvas 自有 FTS5 generation、完整性检查、原子切 active、线性 scan fallback。不应直接复制 LanceDB/GPL 实现。

### 不能直接学的部分

- 它的正文真相是 SQLite，根目录稿件只是发布投影，与 Canvas file-first 所有权不同。
- 写作业务仍主要是 architecture→directory→draft→review/refine→finalize 阶段 prompt，没有 Canvas 级别的 cutoff 人物投影和八项状态人工 commit。
- Canvas 正文 mutation 已有 intent、immutable artifacts、request-hash replay 和 crash recovery；不需要为 core save 再建一套 outbox。Outbox 只在未来有独立 export/publish projection 时才有增量。
- GPL-3.0 代码不复制。

### 裁决

`HIGHEST_VALUE_CLEAN_ROOM_ENGINEERING_REFERENCE`

它是本轮对 Canvas 工程架构增量最大的项目，但不是最强的人物一致性引擎。

## 3. NovWr

### 它真正是什么

NovWr 是 Python/FastAPI/SQLAlchemy/Alembic 后端 + React Web + Tauri/Rust desktop 的完整系统，包含 40 余个 migration 以及 pytest/Vitest/Playwright/安装版验收路径。

关键源码：

- `app/core/continuation_runs.py`
- `app/core/context_assembly.py`
- `app/core/copilot/apply.py`
- `app/core/indexing/lifecycle.py`
- `alembic/versions/034_add_continuation_runs.py`

### 真正值得学的部分

1. **Durable admission record**：continuation run 有 client request ID、canonical request hash、semantic key 活动唯一约束、claim token 和 delivered IDs，防止进程重启后的错误重放。
2. **任务租约和 stale reclaim**：queued/running 任务有 claim、续租、过期回收、quota settlement 与 interruption 记录。
3. **索引 freshness contract**：索引保留 revision/built revision/status/error，可检测 stale job，有 readiness 与构建指标。
4. **确定性上下文召回**：使用 Aho-Corasick 命中名称/别名，歧义别名禁用，最长命中优先，再按 visibility 投影 surface/hidden/reference。
5. **人工建议依赖事务**：Copilot 先产生 preview/actionable suggestion，人工选择 apply；建议及其依赖在 nested transaction 内执行，stale target 或依赖失败会回滚。

### 对 Canvas 的实际价值

Canvas 的长篇 analysis run 已有 provider/source revision pin、request hash、`submission_unknown`、人工对账后替换和逐批人工 review。但如果进程在持久化 `executing/submitting` 后突然退出，当前记录没有 TTL/heartbeat，也无法转成合法的替换态。NovWr 的 claim/lease 协议可用于补这个真恢复缺口。

正确落法必须是：过期执行只转人工对账态，绝不自动重发请求。

### 不能直接学的部分

- Chapter 与 world model 均以数据库为 owner，不能与 Canvas 双写。
- 上下文默认约 100k token 字符估算与 tail-drop 太宽，不能取代 Canvas 的 hard-canon fail-close pack。
- continuation postcheck 是 advisory warning，不等于正文 save gate。
- 正文没有与 Canvas `expectedRevision + SHA + contextPackFingerprint` 等价的绑定。
- AGPL-3.0 代码不复制。

### 裁决

`ADAPT_DURABLE_RUN_AND_INDEX_LIFECYCLE`

学长任务恢复和索引 freshness；候选依赖图只在 Canvas 出现真实多对象原子更新需求时再做。

## 4. probable OCNovel

### 它真正是什么

OCNovel 是 MIT 许可的 Python/PySide6 桌面写作管线，具有 outline/content/audit/revise/finalizer、FAISS 知识库、三级大纲、伏笔字段和相对丰富的中文网文质检。

关键源码：

- `src/generators/outline/outline_quality_gate.py`
- `src/generators/outline/outline_auditor.py`
- `src/generators/content/thunder_point_validator.py`
- `src/knowledge_base/knowledge_base.py`

### 真正值得学的部分

- 大纲从卷到章的目标、场景序列、POV、伏笔埋设/最后出现/回收信息；
- 结构与内容质检分离，且有报告与重试管线；
- 质检分类覆盖 POV、大纲重复、空洞章纲、段落/句式、AI 高频语、人设矛盾、主线偏离、节奏、雷点等；
- 启发式规则与 LLM 语义检查分路，可以节省审查 token。

### 不能直接学的部分

- “前 600 字动作词数”、固定对话比例、特定 AI 短语、段落长度等默认阈值高度题材化，对悬疑、文学、历史或刻意慢节奏作品容易假阳性。
- 质检异常有些路径采“报警但不阻断”，不能当成 Canvas P0 门禁。
- FAISS/pickle/MD5 cache 没有 Canvas 需要的 source receipt、active generation 和重建切换协议。
- 生成/审计/修订后直接写文件，没有 revision pin、CAS 和人工状态 commit。

### 裁决

`ADAPT_QUALITY_TAXONOMY_ONLY`

只学“诊断分类、可配置严重度、报告化”，不复制阈值、prompt、RAG 或状态引擎。

## 5. AI_NovelGenerator

这是 AGPL-3.0 的 CustomTkinter/Python 工具。其流程是架构→章节蓝图→近期摘要/RAG→草稿→finalization；关键文件为 `novel_generator/chapter.py`、`novel_generator/finalization.py`、`novel_generator/vectorstore_utils.py` 和 `consistency_checker.py`。

优点是 provider/embedding adapter 比较多，支持分阶段恢复，且单文件采用临时文件替换。但其上下文主要是最近 3 章、末尾字符、少量关键词与 RAG 片段；`character_state.txt` 和 `global_summary.txt` 由 LLM 直接重写，两文件与向量更新不是一个事务。一致性检查也主要是 prompt 评估，没有结构化 diff/不变式/人工 commit。

`vectorstore_utils.py` 还包含修改进程级 SSL default context 为 unverified 的 helper，向量库清理直接递归删除目录，不适合作为 Canvas 安全/恢复模板。

裁决：`REFERENCE_ONLY`。

## 6. RWKV-Runner

RWKV-Runner 是 MIT 的 Go/Wails + React + Python/Rust 本地推理平台，关心 completion、batch、embedding、模型管理、转换/微调和 recurrent state cache。`backend-python/routes/completion.py`、`backend-golang/batch_completion.go` 和 `backend-python/albatross_engine/state_cache.py` 都属于模型运行时，不是小说正典。

必须防止概念混淆：RWKV recurrent/prefix state 是模型推理状态，不是角色状态、知情账或伏笔记忆。它对 Canvas 唯一的潜在价值是本地 provider/OpenAI-compatible endpoint 适配参考，而 Canvas 已有 provider/LLM 路由。

裁决：`PROVIDER_REFERENCE_ONLY`。

## 7. MuMuAINovel（ddys）

### 比 Grok 原摘要更强的地方

该仓已有实质性的长篇领域模型：

- `backend/app/models/character_known_info.py`：知情条目含 source type、learned chapter、confidence、secret level；
- `backend/app/models/narrative_promise.py`：承诺/谜团/冲突含 status、deadline chapter、last activated chapter 和 resolution；
- `backend/app/models/chapter_causal_link.py`：结构化 cause→event→effect→decision；
- `backend/app/services/narrative_state_service.py`：按 `< current chapter` 投影 POV 知情，重分析时按章回滚关系事件/因果/时间线/知情/承诺，并阻止低章直接覆盖高章状态。

这些是真正可学的业务概念，尤其是知识获得来源、叙事承诺过期和重分析回滚语义。

### 为什么仍不能接管 Canvas

- AI 正文直接写 `Chapter.content` 并 commit，然后启动分析。
- 分析结果经多次 DB commit 保存 analysis、memories、entities，再 settle 叙事状态，最后另行写 vector DB；正文、状态与向量没有共同 source revision 事务。
- LLM analysis 直接变成 durable state，没有 Canvas 的 evidence-bound candidate/human accept。
- 章节普通更新没有 expected revision、content hash 和 context receipt，无法防多 AI 静默覆盖。
- GPL-3.0 代码不复制。

裁决：`DOMAIN_MODEL_REFERENCE_ONLY`。学业务字段/诊断，不学自动 settle 和 DB owner。

## 8. MuMuAINovel（xiamuceer）

该仓更偏多用户 Web，有 PostgreSQL/SQLite 路径，实现角色、记忆、伏笔、职业等级与自动状态更新。关键源码包括 `backend/app/services/foreshadow_service.py`、`memory_service.py` 和 `character_state_update_service.py`。

伏笔字段有 planned/planted/resolved/partial/abandoned 等生命周期、目标/实际回收章和紧急度，工作台概念可供 Canvas UI 参考。但这些状态仍由服务/LLM 分析后直接更新数据库，且当前快照没有真正的 test directory/测试文件作为同等强度证据。

裁决：`UX_AND_DOMAIN_REFERENCE_ONLY`。

## 9. 马良 AINoval

当前 commit 只有 `README.md`。Flutter/Spring/MongoDB/多 Agent/知识图谱都只是文档声称，没有可审计的源码、Schema、测试、CI 或 LICENSE 支撑。

裁决：`UNVERIFIED_IMPLEMENTATION_DO_NOT_LEARN_FROM_CLAIMS`。
