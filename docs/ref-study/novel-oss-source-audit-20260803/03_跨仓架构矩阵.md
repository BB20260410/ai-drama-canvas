## 两种排名必须分开

### 对 Canvas 的工程增量

1. **AI-Novel-Writer** — 索引代际、outbox/冻结快照、项目租约、安全发布。
2. **NovWr** — durable run、claim/lease、stale reclaim、index freshness、建议依赖事务。
3. **InkOS** — compose trace、rule precedence/override、创作与 state settlement 职责分离。
4. **MuMu ddys** — 知情 provenance、因果链、叙事承诺过期。
5. **probable OCNovel** — 中文网文质检分类和步骤 UX。

### 作为“百万字一致性内核”的匹配度

1. **Canvas 当前内核** — 唯一具备 cutoff pack→preflight→chapter CAS→evidence candidate→human state commit→rebuild 闭环的系统。
2. **NovWr/InkOS/MuMu 的局部机制** — 各自有用，但都没有超越 Canvas 闭环的整体证据。
3. **AI-Novel-Writer** — 工程强，但人物时态正典业务较弱。
4. **OCNovel/AI_NovelGenerator** — 质检或 prompt+RAG 工具，不是安全状态内核。

因此，“架构设计成熟”和“适合做 Canvas 的人物一致性 owner”是两个不同问题。

## 代码可用与架构可学的法律/工程边界

| 类型 | 本轮决定 |
|---|---|
| GPL/AGPL 源码 | 不复制、不逐行翻译、不链接 Canvas runtime；只提取公开协议思路，clean-room 独立实现 |
| MIT 源码 | 法律上更宽松，但仍不因“能复制”就复制；OCNovel/RWKV 与 Canvas 所有权和业务不匹配，没有净收益 |
| 无 LICENSE/无实现 | 不使用，也不将 README 声称当架构证据 |
| Prompt/质检语料 | 不复制字面内容；只把“POV、重复、节奏、雷点”等一般性分类转化为 Canvas 自有的可配置诊断 |

## 对“100 万字不崩”的边界

没有任何一个仓库的字段数、Agent 数、测试数或 RAG 存在本身能证明百万字一致性。可信的证明必须来自：

- 确定的时态投影与 future leak 阻断；
- 硬正典/必备角色不可被预算挤掉；
- 正文与状态分别有冲突检测与人工所有权；
- 修章后下游状态可失效、重放、校验与原子 promotion；
- 派生索引可重建且不变成第二正典；
- 长时任务在断电/进程崩溃/回执不明时不会重复执行；
- 对真实长篇做性能、召回、一致性、修章和多 AI 互踩测试。

Canvas 已经覆盖前四项的大部分；本轮建议主要补第五、第六和更可解释的 pack 可观测性。
