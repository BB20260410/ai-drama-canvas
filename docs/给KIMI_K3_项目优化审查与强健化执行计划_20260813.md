# 给 Kimi K3 的项目优化、审查与强健化执行计划

更新时间：2026-08-13
适用仓库：`/Users/hxx/Documents/无限画布`
主执行模型：Kimi Code CLI `0.35.0`，模型 `kimi-code/k3`
辅助审查席：Grok 4.6、豆包订阅 GLM 5.2、豆包

## 一、直接结论

Kimi K3 不只能做前端。它适合承担以下四类工作：

1. **直接实现前端质量切片**：Vue 状态、交互、无障碍、性能、异步竞态、组件拆分和 Renderer 测试。
2. **直接实现低风险工程质量切片**：纯 TypeScript 工具、测试夹具、基准探针、确定性校验脚本和开发文档。
3. **只读审查高风险后端边界**：Core、Main、preload、MCP、SQLite、锁、事务、安全与构建交付；输出复现和接口需求票，不直接改 Owner。
4. **验证与取证**：定向测试、隐藏 Electron UI、键盘/焦点、错误态、资源释放、性能指标和无敏感信息证据。

但“能写”不等于“适合独立改”。这个项目已经有成熟且高风险的 Studio Owner、SQLite 账本和交付合同。让 Kimi 跨层随意重构，收益小于回归风险。默认原则固定为：

- Kimi 在独立 Git worktree 中作为唯一写者。
- 一次只处理一个经复现的问题。
- 前端和纯工具可以写；高风险 Owner 默认只读。
- 没有复现就不改代码；没有红绿证据就不宣称修好。
- Kimi 不能给自己的实现独立判定最终 PASS。
- Grok 4.6、GLM 5.2、豆包只提供独立审查、复现设计和交叉复核，不与 Kimi 共同写工作树。

Grok 4.6 是本轮已用本机 CLI 只读确认的可选模型。GLM/豆包本轮只核对了适配器和历史有效回执，没有消耗订阅重新调用；每个实际批次必须先做一次最小身份探针。返回身份不符、无正文、限流或通道失败时，标记 `BLOCKED/NOT_VERIFIED`，禁止静默换成其他模型。

### 3.2 角色分工

| 角色 | 主要责任 | 写入权限 |
|---|---|---|
| Kimi K3 | 主计划、Renderer 审查、确认票实现、定向测试、自审交接 | 独立 worktree 唯一写者 |
| Grok 4.6 | 对抗式复核：竞态、绕过、重复副作用、退出、证据假通过、安全边界 | 只读；只输出结构化报告 |
| GLM 5.2 | Core/Main/IPC/SQLite/事务/锁序/failed-unknown/恢复合同审查 | 只读；只输出结构化报告和红测设计 |
| 豆包 | 用户流程、按钮/错态/空态、可访问性、中文文案和模块覆盖 QA | 只读；只输出结构化报告 |

辅助模型不直接操作 Git、不运行写命令、不修改源码。Kimi 只能把它们的报告作为候选证据，不能把多数意见当事实。

### 3.3 四阶段协作

1. **盲审**：Kimi、Grok、GLM、豆包读取同一个脱敏审查包，彼此看不到报告。
2. **裁决**：Kimi 去重并做最小复现；只有确认问题进入实现。
3. **实现**：Kimi 单独写一个已批准前端/纯工具票；其他三席保持只读。
4. **交叉复核**：Grok 检查绕过和竞态，豆包检查用户体验，GLM 检查跨层合同；Kimi 根据新证据最多纠正两轮。

每个辅助模型每轮最多给出 5 个 P0–P2、3 个 P3。超出范围的意见忽略；没有复现依据必须标 `hypothesis`。

### 3.4 调用参数

| 模型 | 参数 |
|---|---|
| Kimi K3 | 审查用交互式 `--plan`，实现用隔离 worktree 的 `--auto`；禁止 `--yolo`；CLI 不暴露 temperature |
| Grok 4.6 | `--model grok-4.6 --reasoning-effort high --permission-mode plan --disable-web-search --no-memory --no-subagents --max-turns 12`；使用 JSON Schema；若 CLI 拒绝某参数则记录真实降级，不换模型 |
| GLM 5.2 | `--role glm --model glm-5.2 --temperature 0.2 --top-p 0.95 --reasoning-effort high --max-tokens 24576` |
| 豆包 | `--role doubao --model doubao-seed-evolving --temperature 0.3 --top-p 0.95 --reasoning-effort high --max-tokens 16384` |

GLM 和豆包共用一个订阅适配渠道，必须串行调用。Grok 可以与 GLM/豆包的只读审查并行，但不得与 Kimi 的写入阶段并发。所有 Electron、SQLite 锁测试、build 和性能测试仍串行。

每个辅助席在一个批次内默认只有三次机会：一次最小身份探针、一次盲审、一次修复后复核。只有出现新的、可复现证据时才允许追加一次定向纠正；禁止让模型彼此无限对话或反复重审同一份未变化代码。所有调用都由 Kimi 发起和收口，辅助模型之间不能直接委派任务。

### 3.5 审查包和输出安全

- 输入只包含相对路径、目标文件、当前 diff、测试摘要和必要合同；不得上传正式工程、正文、CAS、凭据或本机绝对路径。
- 原始模型输出写入忽略目录的单次运行文件；最终只保留脱敏后的 JSON 摘要。
- 每份报告必须记录 requested model、returned model、输入 SHA、exit code、finish reason 和 `notVerified`。
- Grok 使用 CLI 的 JSON Schema；GLM/豆包适配器不原生强制 Schema，因此输出后必须先做 JSON 解析和必填字段校验。一次定向纠正后仍无效就标 `BLOCKED`，不能循环调用。
- 模型探活只证明“通道和身份可用”，不证明审查或实现完成。

## 五、Kimi 可以承担的全部前端任务

### 5.1 Vue 状态和异步竞态

- 审查所有 `watch`、`onMounted`、`onBeforeUnmount` 和异步回填。
- 检查 root 切换、筛选变化、翻页、搜索、快速选中、卸载后的迟到 Promise。
- 为每条异步流建立 `projectRoot + query + generation/epoch` currentness。
- 检查 loading/error/empty/disabled/retry 状态是否互相覆盖。
- 检查同一动作连点、双击、键盘回车与鼠标点击是否造成重复 IPC。
- 验证失败后可恢复，不把旧结果或旧错误回填到新工程。

### 5.2 交互和产品可用性

- 全模块按钮可用、禁用、加载、空态、错误态和重试态矩阵。
- 菜单、弹窗、抽屉、页签、分页、搜索、筛选、导入、导出和撤销/重做。
- 关闭弹窗后焦点恢复；Escape、Enter、Space、Tab、Shift+Tab 正常。
- 危险操作有明确确认；不可用动作解释原因。
- 错误文案可操作，不展示内部路径、SQL、token 或堆栈。

### 5.3 无障碍和响应式

- 语义标签、可访问名称、`aria-*`、`role`、`aria-busy`、live region。
- 键盘全流程、焦点陷阱、焦点可见性和弹窗返回焦点。
- 1280×760、小窗口、200% 缩放、长中文、空数据和极端错误文案。
- 深浅主题对比度、`prefers-reduced-motion`、禁用态可辨识度。
- 不以颜色作为唯一状态表达。

### 5.4 Renderer 性能

- 响应式依赖面：避免大对象深响应，合适时使用 `shallowRef`。
- 热路径：避免 playhead、pointermove、zoom、scroll 每帧全量扫描。
- 索引/缓存：按 revision 或 generation 失效，不缓存真相源。
- 列表：分页替换 DOM、视口惰性、缩略图 lazy/async、对象 URL 有界释放。
- 更新：同一刷新批次最多一次昂贵同步；使用 rAF 或微任务 owner 合并。
- 取消：切工程、筛选、卸载后停止无用任务；限制 IPC 在途数量。
- bundle/chunk：先测量，再决定是否预加载或拆包；不凭 bundle 大小猜瓶颈。

### 5.5 组件结构和可维护性

当前大型 Renderer 文件包括：

- `ManagedStudioCanvasView.vue`：约 7303 行。
- `MaterialStudioView.vue`：约 3337 行。
- `App.vue`：约 3034 行。
- `StudioContinuityReviewView.vue`：约 1790 行。
- `VideoEditorView.vue`：约 1701 行。

Kimi 可以做有界拆分，但必须遵守：

- 一次只拆一个清晰职责，例如 playback controller、媒体分页状态、焦点控制、纯 projection mapper。
- 先冻结行为测试，再移动代码。
- 优先抽纯函数、纯合同、composable 和 controller；不要先拆模板。
- 不改变 DOM 层级、testid、ARIA、IPC 参数、Store Owner 和错误语义。
- 一个切片应能独立回滚；禁止“大文件看着不舒服”式全局重构。

### 5.6 前端测试强健化

- 把修改范围内脆弱的源码字符串断言升级为行为测试。
- 使用 deferred Promise 稳定复现迟到、乱序和卸载竞态。
- 使用语义 locator，不依赖 CSS 层级或随机延时。
- 监听 console error、page error、unhandled rejection。
- 每个关键修复至少有：原始红测、修复绿测、相邻回归。
- 不默认新增 `@vue/test-utils`；优先复用现有 Vitest、jsdom、Playwright 和纯控制器测试。

### 5.7 内存与资源释放

- 定时器、rAF、ResizeObserver、MutationObserver、全局事件监听器。
- object URL、audio/video 元素、媒体事件、pointer capture。
- 切根/卸载后的队列、Promise 回调和预览任务。
- 重复进入模块 20 次后监听器、计时器、DOM 和 Renderer RSS 不持续增长。

## 六、前端之外，Kimi 还可以做什么

### 6.1 测试架构

- 建立隔离 fixture 和 deterministic deferred helper。
- 整理 UI 功能矩阵、测试覆盖地图和缺口索引。
- 清理 flake：固定时钟、稳定 locator、显式状态等待、独立 userData。
- 为一个模块建立最小 Page Object 或 fixture；不全仓一次改造。
- 设计 failure injection：IPC 拒绝、Promise 乱序、资源解码失败、工程切换、卸载。

### 6.2 开发工具和静态分析

- 只读统计组件体积、依赖扇出、循环 import、未清理 listener、重复 watcher。
- 写无副作用的 AST/静态检查，防止 Renderer 直接导入 Core Owner。
- 写性能计数器或基准 fixture；默认关闭，不进入产品响应。
- 检查测试是否只做字符串匹配、是否遗漏真实行为断言。
- 检查证据输出是否含本机路径、正文、URL 或凭据字段。

### 6.3 文档和开发者体验

- 维护组件职责图、状态机图、错误态矩阵、键盘操作表。
- 输出接口需求票，避免前端为了缺接口自行推导真相。
- 记录真实命令、测试结果、未验证项和回滚办法。
- 更新修改切片的 README 或注释；不把实现过程堆进用户文案。

### 6.4 只读后端/安全/交付审查

Kimi 可以独立寻找：

- IPC actor/effect 分类漂移；
- command failed/unknown 语义误判；
- SQLite 事务外 currentness 检查；
- watcher 重复计算或 close 不排空；
- 出站 URL/DNS/TLS/凭据泄露；
- package/candidate 证据假通过；
- 崩溃后重复副作用或无法恢复。

但最终产物是 finding 或红测设计，不是直接修改这些 Owner。

## 七、首批建议任务池

以下均为“候选任务”，不是已确认缺陷。Kimi 必须先复现，再决定是否实现。

### K3-AUDIT-01：Renderer 健康地图

目标：用一次只读审查建立当前真实风险地图，不做全面重构。

检查：

- 前 10 个大型 SFC 的职责、watcher、异步流、全局 listener、timer、observer。
- 修改范围内哪些测试是行为测试，哪些只是源码字符串断言。
- 根切换、筛选、卸载、错误恢复的 currentness 合同。
- 性能热路径是否有可测量的 O(N) 或重复同步。

输出：最多 8 个 P0–P2 finding、5 个 P3 建议；其余写 `hypothesis`。没有确认问题时允许输出 PASS，不为制造工作而改代码。

### K3-PERF-01：VideoEditor 播放热路径测量与有界优化

当前源码可见候选：playhead 更新会读取 active subtitle、overlay、audio，并调用 preview 同步；播放 tick 为 80ms。它可能在合法大时间线下形成重复 O(N) 扫描，但目前不是确认缺陷。

先测：

- 1000 clips / 16 tracks fixture。
- 每秒全量 clip 扫描次数、`syncPreview` 调用次数、p95 tick 时间、长任务数。
- 播放、seek、拖动、暂停、切工程、卸载后的任务收敛。

只有复现超预算或重复同步才改：

- 按轨道维护 revision-bound 索引或活动窗口；
- 播放调度统一到 rAF；
- 每视觉帧最多一次 preview sync；
- 编辑/reorder 后明确失效；
- 保留现有媒体漂移校正。

验收：性能有实测改善且行为等价；若没有明显收益，撤回实现，仅保留基准测试。

### K3-REL-01：Renderer 资源释放审计

目标：重复进入/离开 VideoEditor、Canvas、全局资源和 Review 模块后，资源不累计。

检查：

- timer/rAF、window listener、ResizeObserver、MutationObserver；
- object URL、video/audio element；
- pending queue、deferred callback、root-scoped cache。

验收：20 次进入/离开后计数回到基线；旧 root 无回填、无错误弹窗、无 console/page error。

### K3-RACE-01：异步 currentness 行为测试

选择一个未充分覆盖的 Renderer 流，构造：

- A 请求慢、B 请求快；
- 同 root 查询变化；
- A root → B root → A root；
- 请求中卸载；
- 失败响应迟于成功响应。

只有测试先红才补 token/generation。一次最多修一个 owner，禁止全仓批量加 token。

### K3-A11Y-01：全模块键盘与焦点矩阵

## 八、推荐执行顺序

不要把上面所有任务一次性执行。建议一个 Kimi 批次只做以下顺序：

### Phase 0：隔离与冻结

由主集成者创建独立 worktree；Kimi 不进入主工作树写入：

```bash

git status --short
git rev-parse HEAD
git worktree add -b codex/kimi-k3-quality-20260813 ../无限画布-kimi-k3 "$(git rev-parse HEAD)"
```

启动后记录：

- HEAD；
- `git status --short`；
- `release-manifest.json`；
- Kimi CLI 版本和实际模型 ID；
- 本批次唯一文件所有权。

若主工作树不干净或分支已存在，停止创建，不猜测、不 reset。

### Phase 1：只读审查和基准

先执行 `K3-AUDIT-01`，再在 `K3-PERF-01`、`K3-REL-01`、`K3-RACE-01` 中选择最多两个最有证据的票。

完成标准：

- finding 有源码证据或确定性运行复现；
- 与当前 Owner/已关账报告对比，不重复旧问题；
- 有明确红测；
- 没有复现则结束为“无代码变化的审查完成”。

### Phase 2：单票实现

- 一次只领取一个 confirmed finding。
- 先让红测失败，再写最小实现。
- 只改批准文件；需要新 IPC/Core 接口时停止并写接口需求票。
- 不顺手格式化，不更新依赖，不做第二项重构。

### Phase 3：相邻验证

顺序执行：

1. 新增红绿测试。
2. 同模块相邻回归。
3. `npm run typecheck:app`。
4. `npm run typecheck`。
5. `git diff --check`。

涉及真实 Renderer 行为时，再跑隔离隐藏 Electron UI；涉及 startup/Canvas/投影性能时，重建后只跑一次新身份严格 T23。普通票不要每次跑全量四分区。

### Phase 4：自审与交接

Kimi 必须：

- 逐文件解释改动和不变量；
- 列出真实命令与结果；
- 列出未运行项；
- 扫描敏感信息和绝对路径；
- 确认无运行进程、临时锁、fixture 残留；
- 输出 commit-ready diff，但默认不 stage、不 commit、不 push。

### Phase 5：独立验收

主集成者审查 diff，并独立复跑最小红绿测试。只有通过后才决定移植或 cherry-pick。Kimi 自己的 PASS 不能替代独立验收。

## 九、防止死循环和范围失控

1. 同一失败最多两轮纠正。
2. 第二轮仍是同一根因，停止修改并登记 `BLOCKED`。
3. 不重复启动已在运行的测试；先检查 PID/进程。
4. 不因测试无输出立即重跑；确认进程状态和退出码。
5. 每个 finding 必须有唯一指纹：owner + 触发条件 + 失败状态。
6. 没有新证据不升级严重级别、不升级重构范围。
7. 一个切片最多 8 个生产文件，超过则重新拆票。
8. 测试失败必须区分：产品回归、测试漂移、环境阻塞、旧构建。
9. 不把 plan、源码存在、typecheck 或字符串断言当成功能完成。
10. 不通过增加重试、并发、sleep、timeout 掩盖竞态或性能问题。

## 十、测试和完成门

### 10.1 普通 Renderer 切片

- 原始红测可稳定复现。
- 修复后红测和相邻测试 PASS。
- `npm run typecheck:app` PASS。
- `npm run typecheck` PASS。

### 10.2 性能切片

### 10.3 UI/无障碍切片

- 鼠标和键盘路径均通过。

### 10.4 最终边界

只有以下条件全部满足，才能写 `COMPLETE`：

- 本批次确认的 P0/P1 为 0；高价值 P2 已关闭或明确阻塞。

- worktree 无未解释文件和运行进程。

## 十五、我建议 Kimi 第一批实际执行什么

优先执行一个小批次，而不是“全面优化全部代码”：

1. `K3-AUDIT-01`：Renderer 健康地图。
2. 同源盲审：Grok 4.6 查竞态与证据绕过，GLM 5.2 查跨层合同，豆包查真实用户流程。
3. Kimi 去重并实际复现；若实测成立，执行 `K3-PERF-01`：VideoEditor 大时间线播放热路径。
4. 同批补 `K3-REL-01`：VideoEditor/Canvas 资源释放测试，但只修一个确认问题。
5. 修复后由 Grok 与豆包交叉复核前端副作用，GLM 只检查接口合同是否漂移。
6. 不在第一批触碰 `ManagedStudioCanvasView.vue` 启动链、Core/Main/SQLite 或交付脚本。

这组任务的理由是：VideoEditor 当前不受 T23 首卡 13ms 余量直接约束，存在可明确测量的高频路径，也能用纯 Renderer/controller 测试闭环；即使最终没有缺陷，基准和资源释放测试仍有独立价值。相比再次重构整个项目，它的风险更低、结论更可信、回滚更简单。
