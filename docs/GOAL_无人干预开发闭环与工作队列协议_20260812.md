# GOAL · 无人干预开发闭环与工作队列协议（2026-08-12）

> 目标：让本仓库具备「巡检产票 → agent 领票 → 修复验证 → 证据销项 → 巡检再产票」的
> 无人干预全链路软件开发闭环，支持长期复杂任务自主执行与漏洞迭代全流程。
> 对标机制：Qwen3.8-Max oh-my-cli 的 Loop Engineering（需求/反馈/自测 → issue → 自动领取 → 执行 → 测试 → 修复 → 迭代）。

## 与既有协议的关系

- 本协议是 `docs/GOAL_自动续跑与恢复协议.md` 的**增补层**，不替代 STATUS/TASKS 磁盘真相源。
- `STATUS.md` / `TASKS.md` 仍是**规划层**真相源（goal、earliest、gate）。
- `WORKQUEUE.json` 是**缺陷/工作项层**真相源：自我生长、机器可解析、由巡检自动写入。
- 热路径宪法 `scripts/goal-resume-prompt.txt` 升级为 v3，接入工作队列循环。

## 架构（四件套）

| 组件 | 文件 | 职责 |
|---|---|---|
| 工作队列状态机 | `scripts/workqueue-ops.ts` | 领取/验证/销项/豁免/停放/租约回收；anti_loop 上限 |
| 缺陷台账 | `WORKQUEUE.json` | 唯一工作项真相源（机器可解析） |
| 巡检器 | `scripts/auto-triage.ts`（`npm run patrol`） | 有界探针 → 失败自动建票/复现重开 |
| 唤醒 | 定时任务 + Stop 闸 + scheduler | 周期触发巡检与领票续跑 |

运行日志与巡检证据落 `.workqueue/`（日志、指纹、verify log、patrol summary）。

## 工作项状态机

```
open → claimed → verifying → closed
  ↑        │          │
  │        └── verify FAIL → claimed（attempts+1）
  │                    └→ attempts≥4 → parked（anti_loop，禁止原样重跑）
  └─ reap（租约 24h 过期）/ 巡检复现已 closed 缺陷 → reopened-by-patrol
closed/waived 项再次被巡检命中 → 自动 reopen（漏洞回归即回流）
```

字段合同：`id / status / severity(P0–P3) / source / probe / fingerprint / repro / owner / leaseUntil / attempts / history / evidence`。

## 领票 → 销项纪律（agent 硬规则）

1. 每轮先看 `npm run workqueue:next`；有 actionable 项且 repro 可自执行 → **立即领取**。
2. claim 必须给 `--who` 与真实 `--repro`（修复验证命令），禁止空 repro。
3. 修复是**有界切片**：只改缺陷相邻代码，不扩域、不重建 owner、不动已关账 final-validation。
4. 销项必须 `verify`（重跑 repro，exit 0）→ `close --evidence=<路径>`；证据落 `docs/evidence/` 或 `.workqueue/`。
5. verify 连续失败 ≥4 次自动 parked；禁止原样重跑同一失败。
6. 涉及真实付费调用（imagegen）或 Git 提交的缺陷 → `waive --why` 或 park 并注明「需用户授权」，不得自动执行。
7. parked/waived 项不消失：每轮 stats 可见，供用户或后续切片拣回。

## 多会话协调（2026-08-12 实战增补）

定时任务与人工会话共享同一队列，必须防双修竞态：

1. 领取前先 `workqueue:list` 看 owner 与 notes；票已被他人 claimed → 不重复领取，可补 note 协助。
2. 修复中发现目标文件被并行会话修改（mtime 新于自己上次读）→ 立即停手，用 `note` 登记已做/未做与移交意图，由 owner 完成 verify/close。
3. 同一票的源码改动只允许一个会话落盘；测试合同修正与源码修正可分工，但必须在 notes 互相登记。
4. 巡检已由单飞锁保护（`.workqueue/patrol.lock`）；禁止杀他人巡检进程；重负载分区（fast/medium/integration）verify 前先确认无其他 vitest 在跑，避免 CPU 争抢造成假超时；**同一时刻全机只允许一个重负载分区 verify**，发现他人正在 verify 重分区 → 本轮改做轻活并留 note。
5. 队列写已由 `mutateQueue`（`.workqueue/workqueue.lock` 互斥 + 锁内重读）原子化；直接改 WORKQUEUE.json 的旁路写法（node -e 等）已禁止，必须走 workqueue-ops 命令，否则丢项竞态复发（wq-0007 实测教训）。
6. 巡检卡死处置：`workqueue-ops patrol-health` 报 STALE → 先查心跳相位的探针是否本就重负载；REAP-LOCK → 等下一次巡检自动接管或人工删 `.workqueue/patrol.lock`。

## 完成门

工作队列没有「整目标 completed」——它是永续循环。关账条件只有：
- `stats` 显示 open+claimed=0，且 parked/waived 全部有明确理由 → 该巡检周期绿灯；
- 任何新失败会由下一轮巡检重新产票，循环自动恢复。

## 边界（继承 AGENTS.md 红线）

- 禁止 Git stage/commit/push；禁止付费/上传/公证/发布。
- 禁止回写用户权威参考图与正式剧本目录；禁止覆盖 `docs/evidence/**` 既有 final-validation。
- 巡检与修复不得触碰 `projects/codex-ai-drama-studio` 等正式受管工程数据。
